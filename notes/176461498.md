## 二、实践背景

在使用 Hermes Agent 的过程中发现，仅仅提出：

> “帮我优化这个量化交易系统。”

或者：

> “帮我把个人网站做得更酷。”

虽然 Hermes 能够理解大致方向，但容易出现执行范围过大、修改目标不明确、结果难以验收等问题。

因此，本次实践开始尝试使用更加结构化的任务描述，将需求拆分为目标、文件范围、技术要求、限制条件、执行步骤以及最终验收标准。

***

## 三、实践过程

### 1. 将量化项目的模糊需求拆解为执行任务

以：

`D:\btc-eth-trading-system`

为实际项目进行实践。

没有直接要求 Hermes “优化代码”，而是将任务拆解为多个明确阶段：

```
Audit
→ Design
→ Implement
→ Test
→ Backtest
→ Review
```

并明确要求 Hermes：

* 先理解现有架构
* 明确需要修改的文件
* 不删除已有测试
* 不进行真实交易
* 保留 Strategy A / B / C
* 修改完成后运行测试
* 最终输出修改清单和测试结果

通过这种方式，让 Hermes 从“聊天式回答”转变为“工程任务执行”。

### 2. 使用明确的约束控制 Agent 行为

在量化项目中加入了明确的安全和工程约束，例如：

```
禁止真实交易
禁止真实下单
禁止删除测试
禁止泄露 API Key
禁止为了提高 ROI 而制造过拟合
```

同时要求 Hermes 在修改之前先进行审计，修改之后运行测试。

这使 Agent 的执行范围更加明确，也降低了自主修改带来的风险。

### 3. 将复杂目标拆分为可验收的子任务

例如量化项目的需求没有停留在“提升策略”，而进一步拆解成：

```
数据层
↓
OHLCV
↓
缓存
↓
数据质量检查
↓
回测
↓
策略比较
↓
Train / Validation / Test
↓
Walk-forward
↓
Paper Trading
```

每个阶段都有明确的输出和验收标准。

# Day 5：安全边界与故障恢复——理解 Hermes 授权和审核机制

 

## 一、学习目标

本次学习重点是理解 Hermes Agent 在实际运行过程中涉及的权限、凭据和工具调用机制，并学习如何在 Agent 出现异常、执行偏离或调用失败时进行中断、判断和恢复。

通过实践，进一步认识到：

**Agent 能做什么，不仅取决于模型能力，也取决于它被授予了什么工具、权限以及外部服务凭据。**

***

## 二、学习内容

HermesCN 将“权限与凭据”列为第一阶段的最后一课。第一阶段整体目标就是在完成首次对话和可验证任务的同时，理解 Hermes 的权限与安全边界。

本阶段关注的核心问题包括：

```
```

```
Agent
 ↓
模型
 ↓
Tools
 ↓
Credentials
 ↓
外部服务
 ↓
真实操作
```

因此，在使用 Hermes 时，不能只关注“模型能不能完成任务”，还需要关注：

*  Agent 是否拥有执行某项操作的工具； 
*  工具是否需要 API Key、Token 等凭据； 
*  凭据是否被安全保存； 
*  Agent 是否经过明确授权； 
*  出现异常时能否及时终止； 
*  最终操作是否能够被审核和复现。 

***

## 三、实际实践

### 1. 理解不同操作的权限边界

在前几天的实践中，我使用 Hermes 完成了 Python 项目开发、GitHub 操作、个人网站改造等任务。

实际体验让我认识到，不同任务对应的权限风险并不相同。

例如：

```
```

```
读取代码
↓
风险较低

修改代码
↓
需要更高信任

执行 Shell 命令
↓
需要进一步确认影响范围

Git commit
↓
会改变项目历史

Git push
↓
会影响远程仓库
```

因此，Agent 自动化程度越高，对任务边界的要求也越高。

***

### 2. 学习凭据管理

在使用 Hermes 接入不同模型和服务时，涉及到 API Key、Token 等凭据。

本次学习重点认识到：

> **凭据不应该直接写入代码、README、日志或者公开 GitHub 仓库。**

实际项目中采用 `.env` 等配置方式保存敏感信息，并通过 `.gitignore` 避免将其提交到 Git 仓库。

这一点在此前 GitHub 项目上传过程中也进行了实际验证。

***

### 3. 理解 Agent 工具调用的风险

Hermes 不只是聊天模型，还可以调用：

```
```

```
Terminal
File
Code Execution
Browser
Computer Use
Skills
Memory
```

因此，当 Agent 拥有更多工具时，它能够完成的事情更多，但潜在影响也更大。

例如：

```
```

```
模型回答
    ↓
工具调用
    ↓
实际修改文件
    ↓
执行命令
    ↓
产生外部影响
```

所以真正需要管理的并不是“AI 会不会说错话”，而是：

> **AI 是否有权限把错误真正变成现实操作。**

***

## 四、故障恢复实践

本次学习过程中，我实际遇到过多次 Agent 故障。

例如：

### 模型额度耗尽

GLM-5.2 曾出现：

```
```

```
HTTP 429
您已达到每周/每月使用上限
```

通过判断可以明确：

```
```

```
不是代码错误
不是项目损坏
而是模型 Provider 配额问题
```

之后切换到其他可用模型继续工作。

***

### 免费模型上游拥堵

使用其他免费模型时，又遇到过：

```
```

```
HTTP 429
temporarily at capacity upstream
```

以及：

```
```

```
Upstream idle timeout exceeded
```

此时判断出：

> 问题来自模型服务上游，而不是本地项目。

因此不再重复修改代码，而是：

```
```

```
停止当前 Session
↓
保留本地修改
↓
新建 Session
↓
切换可用模型
↓
继续任务
```

***

### GitHub 推送失败

在网站项目开发过程中还遇到：

```
```

```
Failed to connect to github.com:443
Connection was reset
```

经过排查发现：

```
```

```
本地 Git ✅
本地 commit ✅
远程仓库 ✅
网络连接 ❌
```

最终通过重新建立网络连接后成功 push。

这个过程让我认识到：

> **故障恢复的第一步不是“重做”，而是先判断故障发生在哪一层。**

***

## 五、学到的故障判断方法

逐渐形成了一个简单的排错思路：

```
```

```
发生错误
   ↓
判断是：
模型？
Provider？
网络？
工具？
代码？
Git？
权限？
   ↓
定位故障层
   ↓
保留已经完成的成果
   ↓
只修复故障部分
   ↓
重新验证
```

这比看到错误就直接重装、重跑或者回滚更加可靠。

***

## 六、安全边界认识

通过本次实践，我对 Agent 安全边界有了更明确的理解。

可以把操作分成三个等级：

### 低风险

```
```

```
读取文件
分析代码
生成建议
运行测试
```

### 中风险

```
```

```
修改代码
创建文件
安装依赖
修改配置
```

### 高风险

```
```

```
删除文件
修改关键系统配置
提交代码
Push 到远程仓库
使用真实账户执行外部操作
```

因此，在实际使用 Agent 时，应该让：

> **权限与任务风险相匹配。**

而不是默认让 Agent 拥有所有能力。

***

## 七、个人实践中的安全原则

经过这几天的实践，我总结出自己的几条使用规则：

```
```

```
1. API Key / Token / Secret 永不进入公开仓库

2. Agent 执行高影响操作前必须明确任务范围

3. 修改代码前保留 Git checkpoint

4. 遇到异常首先定位故障层，不直接重装或回滚

5. 尽可能先 Paper / Sandbox，再接真实系统

6. Git push 前检查敏感文件

7. 对 Agent 的工具权限保持最小化
```

尤其是在量化交易项目中，我目前坚持：

```
```

```
Backtest
↓
Paper Trading
↓
验证
```

而不是直接让 Agent 触碰真实交易。

***

本次学习让我认识到：

> **Agent 并不是“会写代码的聊天机器人”，而是一个拥有工具和执行能力的软件系统。**

当 Agent 开始拥有：

```
```

```
Terminal
File
Browser
Code Execution
Git
API
```

之后，它的错误不再只是“回答错误”，而可能变成：

```
```

```

错误执行命令
错误推送代码
错误调用外部服务
```

因此，Agent 使用的关键能力之一，就是：

**控制权限、保护凭据、审查操作、及时中断、正确恢复。**

# Day 7｜结营验收与项目展示：x402 AI Agent Payment Gateway

今天是 Hermes Agent 7 天学习的最后一天，也是这次学习的项目展示日。

这次结营我想展示的项目，是我准备参加 ETHOnline 2026 的一个 Web3 × AI Agent 项目，名字叫 **x402 AI Agent Payment Gateway**。

这个项目目前已经完成了比较完整的产品设计、技术架构、核心流程和开发计划。按照目前的计划，项目会在 2026 年 9 月 5 日正式进入 Hackathon 开发阶段。今天的展示主要记录目前已经完成的产品设计和技术准备，也说明 Hermes 在这个项目里可以怎么参与开发。

这个项目和前几天单独练习 Hermes 的时候有一个比较明显的区别。

前几天主要是在学习 Hermes 怎么使用。到了现在，我开始尝试让 Hermes 服务于一个真实的项目。

这个项目本身也是我这几天学习之后，希望留下来的一个实际成果。

***

## 一、为什么会想到做这个项目

这个项目的出发点其实比较简单。

现在越来越多 AI Agent 开始具备调用工具和访问外部服务的能力。一个 Agent 可以查数据、调用 API、运行代码，也可以根据任务自己决定下一步应该做什么。

但是到了“付钱”这一步，目前很多服务还是围绕人来设计。

例如传统 SaaS API 往往需要注册账号、创建 API Key、绑定信用卡，然后购买套餐。

这种流程对人来说没有太大问题，但如果使用者变成了一个需要自主执行任务的 Agent，情况就会复杂很多。

一个 Agent 如果需要购买一个很便宜的数据 API，每次只需要支付 0.30 美元，那么让人先注册账号，再配置支付方式，再人工确认一次，整个过程就比较麻烦。

我关注到 x402 这个方向以后，就开始思考一个问题：

如果一个 AI Agent 本身可以拥有一个钱包，它能不能在调用 API 的时候自己完成一次非常小额的 USDC 支付？

于是就形成了现在这个项目的核心想法。

Agent 请求一个付费 API。

服务器返回 HTTP 402。

Agent 看到价格和支付要求以后，检查自己的预算。

如果允许支付，就完成一笔 USDC 交易。

服务器验证链上交易。

验证通过以后，再真正执行 API。

整个过程都可以由软件完成。

这就是 x402 AI Agent Payment Gateway 想解决的问题。

***

# 二、这个项目到底在做什么

项目的一句话介绍是：

**x402 是一个 HTTP 402 Payment Gateway，让 AI Agent 能够使用 USDC 微支付自主发现、支付并调用 API。**

项目主要面对三个角色。

第一个是 AI Agent。

它是 API 的消费者，需要根据自己的任务调用外部服务。

第二个是 API Provider。

也就是提供服务的一方，可以把自己的 API 接入 Gateway，并设置价格。

第三个是 Agent Developer。

开发者负责定义 Agent 的行为、预算和安全规则。

整个系统希望形成一个比较完整的机器对机器支付流程。

Agent 访问服务。

Gateway 告诉它需要付多少钱。

Agent 检查自己的预算。

Agent 支付 USDC。

Gateway 验证支付。

API 执行。

最后把结果返回给 Agent。

这样 API 的调用过程和支付过程就连接起来了。

# 三、为什么选择 HTTP 402

这个项目的核心其实就是 HTTP 402。

HTTP 402 的名字就是 **Payment Required**。

虽然这个状态码很早就存在，但过去实际使用并不算广泛。

我觉得它很适合现在的 Agent 场景，因为它本身表达的意思非常直接：

你访问这个资源，需要先完成支付。

所以我们的设计里，当 Agent 第一次请求付费 API 的时候，Gateway 不会直接执行请求。

它会返回一个机器可读的 402 Response。

例如里面会包含支付金额、USDC、接受的网络、支付地址、nonce、request hash 和过期时间。

Agent 拿到这些信息以后，就可以自己决定要不要继续。

这和传统 API Key 模式相比，会更加适合自动化调用。

因为 Agent 不需要先让人类进入后台生成一个长期 API Key。

它只需要根据这一次请求得到的支付要求完成这一次支付。

# 四、项目最核心的一条流程

目前设计的 Demo 流程是这样的。

用户向一个 Research Agent 提出需求。

Agent 决定调用一个需要付费的 Web3 Data Service。

于是 Agent 向 x402 Gateway 发起 POST 请求。

第一次请求没有支付证明，所以 Gateway 返回 HTTP 402。

这个 402 Response 里面写明，这一次请求价格是 **0.30 USDC**。

同时 Gateway 会生成一个 paymentNonce，并计算当前请求的 requestHash。

Agent 收到以后，不会直接付款。

它会先运行自己的 Spending Policy。

目前设计的默认规则是：

每次调用最多支付 0.50 USDC。

每天总预算最多支付 5 USDC。

只允许使用 Hedera Testnet 和 Arc Testnet。

如果当前支付符合这些规则，Agent 才会继续。

之后 Agent 使用 Circle Agent Stack 管理的钱包完成 USDC 转账。

交易发到 Hedera 或 Arc。

交易中会带上对应的 nonce。

交易完成以后，Agent 再向 Gateway 发一次请求。

这一次请求中会加入 `X-PAYMENT-PROOF`。

里面包含交易哈希、payer 地址、网络和 paymentNonce。

Gateway 收到之后，不会相信 Agent 自己提供的信息。

它会直接去链上查询。

检查 transactionHash。

检查 USDC Transfer Event。

检查收款地址。

检查付款金额。

检查 nonce。

这些信息都匹配以后，Gateway 才会真正执行后面的 API。

最后 API 返回 200。

Agent 拿到数据。

整个流程才算完成。

这就是这个项目真正想展示的核心闭环。

# 七、Day 4 的 Profile 和会话管理，也和这个项目有关

# 八、Day 5 的安全边界，在这个项目里是核心问题

这个项目和普通前端项目有一个比较大的区别。

它涉及真实的支付逻辑。

即使 Hackathon 使用的是 Testnet，也不能简单地把支付过程当成一个普通 API 请求。

所以安全部分在 PRD 里面占了比较重要的位置。

第一层是 Agent 自己的 Spending Policy。

目前设置：

`maxPerCall = 0.50 USDC`

`dailyBudget = 5.00 USDC`

`allowedNetworks = ["hedera-testnet", "arc-testnet"]`

如果超过单次预算，或者当天预算已经用完，Agent 就不应该继续签名。

第二层是 nonce。

Gateway 每次生成支付要求以后，会产生一个短期有效的 nonce。

当前设计的过期时间是 5 分钟。

支付验证完成以后，这个 nonce 会从 Redis 删除。

这样可以避免一个已经使用过的支付证明被重复利用。

第三层是 requestHash。

Gateway 会对请求 Body 做 SHA-256。

然后把这个 hash 放进 402 Payment Requirements。

这样支付和具体请求就产生了绑定关系。

如果有人拿一个支付证明去换另一个请求，Gateway 就可以发现对应的 requestHash 不一致。

第四层是链上验证。

Gateway 不会只相信客户端发送过来的 transactionHash。

它会直接通过 RPC 查询链上交易。

检查实际的 Transfer Event。

这部分我觉得也是整个项目比较重要的地方。

# 九、项目为什么选择 Hedera 和 Arc

目前项目主要考虑两个网络：

**Hedera Testnet**

以及

**Arc Testnet**

Hedera 在这个项目里面主要承担支付测试网络的角色。

我们希望 Demo 里面展示真实的 USDC 转账。

Arc 则更多和 Circle Agent Stack 的整体方案结合。

项目希望通过统一的 EVM 接口，把钱包和支付逻辑尽量做成一套。

这样以后切换网络的时候，不需要把整个 Gateway 重写。

所以项目里面专门设计了 `IChainAdapter`。

Gateway 只关心：

验证交易。

检查金额。

检查收款地址。

检查 nonce。

具体怎么通过 Hedera RPC 验证，或者以后怎么通过 Arc RPC 验证，则交给具体的 Adapter。

这样可以把链相关的代码隔离起来。
