## 一、学习目标

本次学习重点是理解如何将自然语言中的模糊需求，转化为 Hermes Agent 能够理解、执行、验证和复现的具体任务。

通过实际项目实践，掌握从：

**模糊目标 → 任务拆解 → 执行约束 → 验收标准 → Agent 执行**

的完整过程。

***

## 二、实践背景

在使用 Hermes Agent 的过程中发现，仅仅提出：

> “帮我优化这个量化交易系统。”

或者：

> “帮我把个人网站做得更酷。”

虽然 Hermes 能够理解大致方向，但容易出现执行范围过大、修改目标不明确、结果难以验收等问题。

因此，本次实践开始尝试使用更加结构化的任务描述，将需求拆分为目标、文件范围、技术要求、限制条件、执行步骤以及最终验收标准。

***

## 三、实践过程

### 1. 将量化项目的模糊需求拆解为执行任务

以：

`D:\btc-eth-trading-system`

为实际项目进行实践。

没有直接要求 Hermes “优化代码”，而是将任务拆解为多个明确阶段：

```
Audit
→ Design
→ Implement
→ Test
→ Backtest
→ Review
```

并明确要求 Hermes：

* 先理解现有架构
* 明确需要修改的文件
* 不删除已有测试
* 不进行真实交易
* 保留 Strategy A / B / C
* 修改完成后运行测试
* 最终输出修改清单和测试结果

通过这种方式，让 Hermes 从“聊天式回答”转变为“工程任务执行”。

### 2. 使用明确的约束控制 Agent 行为

在量化项目中加入了明确的安全和工程约束，例如：

```
禁止真实交易
禁止真实下单
禁止删除测试
禁止泄露 API Key
禁止为了提高 ROI 而制造过拟合
```

同时要求 Hermes 在修改之前先进行审计，修改之后运行测试。

这使 Agent 的执行范围更加明确，也降低了自主修改带来的风险。

### 3. 将复杂目标拆分为可验收的子任务

例如量化项目的需求没有停留在“提升策略”，而进一步拆解成：

```
数据层
↓
OHLCV
↓
缓存
↓
数据质量检查
↓
回测
↓
策略比较
↓
Train / Validation / Test
↓
Walk-forward
↓
Paper Trading
```

每个阶段都有明确的输出和验收标准。

在实际执行中，Hermes 已经完成了数据层建设，并新增了对应测试；整个项目测试数量也从最初的 91 个增加到了 122 个，最终测试结果为：

122 passed

## 六、今日理解

因此，Agent Prompt 本质上已经开始接近一种轻量级的工程任务规范。
