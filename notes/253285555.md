# Day 3｜Hermes Cron 自动化、Notepad 持久化与语义监控｜2026-08-29

## 1. 学习了什么

今天学习并实测了 Hermes Agent 的 Cron 定时任务、任务级 Cron Notepad 持久化，以及基于原始帖子和会话上下文的语义监控。

我理解到，定时监控不是简单地每小时执行一次关键词搜索，而是一条需要逐步校验的自动化链路：

```text
定时触发 → 读取数据 → 校验完整性 → 语义分类 → 读取/更新 Notepad → 决定是否通知
```

今天重点确认了：

- Cron 负责定时触发、独立执行、运行记录和结果投递；
- Cron Notepad 是任务级的持久化 KV scratchpad，可保存跨运行的游标、去重和等级状态；
- 语义监控必须使用原始帖子和上下文重新判断，不能直接信任数据源自带的 `kind`、`classifier` 或其他分类字段；
- `weak_hint`、`strong_preview`、`confirmed` 和 `ignore` 的通知条件不同；
- 数据源失败、过期、字段缺失或上下文不完整时，应采用 fail-closed 策略，而不是把失败误判为“没有新信号”。

## 2. 完成了什么

### Cron 生命周期

我确认了 Hermes Cron 的基本生命周期和主要状态：

- 任务可以按 `every 1h` 持续执行；
- 任务具有 `scheduled`、`completed` 等状态；
- `repeat` 可以限制任务执行次数；
- `deliver` 决定结果的投递目标；
- 任务可以用精确的 `[SILENT]` 抑制本轮投递；
- Cron 任务在独立执行环境中运行，不依赖当前对话持续打开。

### Cron Notepad 持久化

我创建了一个隔离的临时任务，只用于验证任务状态是否跨运行保存。测试没有访问 X、发送 Telegram，也没有修改项目文件。

3. 读取到 `count = 1` 和相同 marker 后，递增为 `count = 2`，marker 保持不变；
4. 重新读取 Notepad，确认写入结果正确；
5. 删除临时任务，确认任务列表为空且该任务的 Notepad 被清理。

# 2026-09-01｜Hermes Agent 多 Agent 协作开发与 Review 实践

今天的重点不是 Backend 技术任务本身，而是记录如何通过 Telegram Topic 调用 Hermes Coding Agent 和 Hermes Reviewer Agent，以及如何在 Coding、Review、Comment 和 MR 流程之间进行协作与权限控制。

## 一、Telegram Topic 的职责划分

本次使用同一个 TJ Robot，但通过不同 Topic 隔离上下文：

- `Parallax 开发调度`：只用于 Coding Agent 开发；
- `Parallax Review`：只用于 Reviewer Agent 审查 PR；
- `Intensive CoLearning`：用于记录共学打卡；
- 不创建新的 Robot；
- 不修改已有 Topic title。

这样做的目的，是让开发、Review 和学习记录分开，避免上下文混乱，也方便之后追溯历史。

## 二、如何使用 Telegram + Hermes Coding Agent

实际流程如下：

1. 在 `Parallax 开发调度` Topic 中发送任务 prompt；
2. 通过 `@parallax-coding` 调用 Coding Agent；
3. 先让 Agent 做预检，确认分支、工作区、stash、任务范围和依赖；
4. 用户确认后，Agent 才开始创建分支和修改代码；
5. Agent 负责：
   - 编写测试；
   - 编写代码；
   - 执行测试、typecheck、lint；
   - 创建 commit；
   - 按规则 pull、push；
6. Agent 完成后汇报修改文件、验证结果、分支和 commit；
7. 创建 MR 前必须暂停，等待用户确认；
8. 合并 MR 前也必须再次暂停，等待用户确认。

### 大白话解释

Coding Agent 就像负责实际施工的工程师：用户先确认施工方案，Agent 才能开始施工；但施工完成并不等于可以自动替用户提交或合并 MR。

## 三、如何使用 Telegram + Hermes Reviewer Agent

实际流程如下：

1. 在 `Parallax Review` Topic 中发送 Review prompt；
2. 通过 `@parallax-reviewer` 调用 Reviewer Agent；
3. 指定仓库、PR 编号、目标分支和最新 head commit；
4. Reviewer Agent 在独立的 Review workspace 中进行只读审查；
5. Reviewer Agent 不修改代码、不创建 commit、不 push、不创建或合并 MR；
6. Review 结果必须包括：
   - `passed: true/false`；
   - blocking issues；
   - non-blocking suggestions；
   - 测试和验证结果；
   - 是否建议进入人工 Review。

### 大白话解释

Reviewer Agent 像独立的验收人员，只负责找问题，不负责改代码，也不能自己批准或合并。

## 四、Review、Comment 与 MR 的协作流程

这些动作必须分开处理：

1. Reviewer Agent 先只返回 Review 结果；
2. 用户阅读 Review 结果，并判断是否采纳；
3. 用户明确回复“采纳 Review 结果”后，Hermes 才生成 GitHub comment 草稿；
4. Hermes 只提供 comment 文本；
5. Hermes 不打开 GitHub comment 页面；
6. Hermes 不点击 `Comment`；
7. 用户自己复制、检查并提交 comment；
8. 创建 MR 是独立动作，必须等待用户确认；
9. 合并 MR 也是独立动作，必须再次等待用户确认。

### 大白话解释

Reviewer 负责发现问题，Hermes 负责起草文字，但最后发送 comment 的动作必须由用户亲自完成。Review 通过、生成 comment、创建 MR 和合并 MR 不是同一个动作，不能自动连在一起。

## 六、今天学到的多 Agent 协作原则

1. Coding Agent 和 Reviewer Agent 必须使用不同 Topic；
2. 一个消息只对应一个清晰任务；
3. Coding Agent 负责实现，Reviewer Agent 负责发现问题；
4. Reviewer 不应该直接修改 Coding Agent 的代码；
5. 用户确认是 MR 创建、Review comment 和 MR 合并的权限边界；
6. 每个 Agent 都必须明确自己的禁止事项；
7. 所有 Review 都应针对明确的 PR、base branch 和 head commit；
8. Topic 隔离可以减少上下文污染和追溯困难；
9. Hermes 可以承担执行工作，但关键外部动作必须保留用户确认。
