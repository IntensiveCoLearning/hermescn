# Day 3｜Hermes Cron 自动化、Notepad 持久化与语义监控｜2026-08-29

## 1. 学习了什么

今天学习并实测了 Hermes Agent 的 Cron 定时任务、任务级 Cron Notepad 持久化，以及基于原始帖子和会话上下文的语义监控。

我理解到，定时监控不是简单地每小时执行一次关键词搜索，而是一条需要逐步校验的自动化链路：

```text
定时触发 → 读取数据 → 校验完整性 → 语义分类 → 读取/更新 Notepad → 决定是否通知
```

今天重点确认了：

- Cron 负责定时触发、独立执行、运行记录和结果投递；
- Cron Notepad 是任务级的持久化 KV scratchpad，可保存跨运行的游标、去重和等级状态；
- 语义监控必须使用原始帖子和上下文重新判断，不能直接信任数据源自带的 `kind`、`classifier` 或其他分类字段；
- `weak_hint`、`strong_preview`、`confirmed` 和 `ignore` 的通知条件不同；
- 数据源失败、过期、字段缺失或上下文不完整时，应采用 fail-closed 策略，而不是把失败误判为“没有新信号”。

## 2. 完成了什么

### Cron 生命周期

我确认了 Hermes Cron 的基本生命周期和主要状态：

- 任务可以按 `every 1h` 持续执行；
- 任务具有 `scheduled`、`completed` 等状态；
- `repeat` 可以限制任务执行次数；
- `deliver` 决定结果的投递目标；
- 任务可以用精确的 `[SILENT]` 抑制本轮投递；
- Cron 任务在独立执行环境中运行，不依赖当前对话持续打开。

### Cron Notepad 持久化

我创建了一个隔离的临时任务，只用于验证任务状态是否跨运行保存。测试没有访问 X、发送 Telegram，也没有修改项目文件。

测试过程和结果：

1. 第一次成功运行读取到空状态，并写入 `count = 1` 和固定标记 `cron-notepad-persistence-v1`；
2. 第二次 Cron 运行先读取原状态；
3. 读取到 `count = 1` 和相同 marker 后，递增为 `count = 2`，marker 保持不变；
4. 重新读取 Notepad，确认写入结果正确；
5. 删除临时任务，确认任务列表为空且该任务的 Notepad 被清理。

一次初始 shell 触发曾返回 `failed` 且没有产生执行记录，因此没有计入测试；随后完成的两次 Cron 执行分别为 `source=direct` 和 `source=builtin`，均为 `completed`。

分类时只使用原始帖子 ID、作者、时间、正文、回复标记、会话 ID、X 原始链接和可用上下文，没有使用 Feed 自带分类字段。

### 语义分类样例

以下分类均由 Hermes 根据原始内容和上下文重新执行：

| 帖子 ID | 类型 | Hermes 分类 | 主要证据 |
|---|---|---|---|
| `2093014447833116908` | 主帖 | `confirmed` | `reseted`、`brand new usage`、ChatGPT Work、Codex、button press，组合起来表达 usage 已恢复或重置已生效 |

- 弱提示出现第二个独立佐证后才通知；
- 同一帖子同一级别重复出现不通知；
- `soon, but not today`、`not today`、`not yet` 等否定表达抑制升级。
