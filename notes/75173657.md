# 2026-08-29

Day 3：将模糊需求转成 Hermes 可理解的执行任务

## 完成内容

1. **Prompt 结构化实践**：今天的核心任务是学习如何把一句模糊的中文需求转化为 Hermes 可精确执行的指令。以"帮我看看最近 GitHub 上有没有值得关注的 AI Agent 项目"为例，逐步拆解为：搜索关键词确定（AI agent framework 2026）、搜索工具选择（web_search + web_extract）、筛选标准定义（stars > 500, 最近 30 天更新）、输出格式约束（表格化：项目名、描述、stars、链接）。最终用 execute_code 在一个脚本里串联搜索和提取，完成端到端的信息收集。

2. **任务边界划分练习**：刻意对比了两种写法的执行效果。模糊写法"帮我分析一下这个项目" → Hermes 会自主决定分析维度，结果可能偏离预期。结构化写法"分析这个 GitHub 仓库的：a) 代码语言占比 b) 最近 10 次 commit 的主题 c) open issues 中标注 bug 的数量" → 结果精确可控。关键是：验收标准要可量化。

3. **多步骤任务编排**：用 tod 工具将一个复杂的"调研竞品并生成报告"任务拆分为 5 个子项，每项有明确的完成标准。配合 delegate_task 并行执行信息收集，再用 execute_code 做汇总合并。整个流程从模糊需求到结构化产出，走了"需求拆解 → 工具选型 → 并行执行 → 结果聚合"的完整链路。

4. **上下文工程实践**：在 delegate_task 的 context 参数中练习了"一次交代清楚"的写法。发现子 Agent 如果缺少关键上下文（比如目标受众、输出语言、格式偏好），会自行脑补导致偏离。好的 context 应该包含：任务目标、约束条件、参考样例、明确的拒绝标准（什么不需要）。

## 学习收获

- **"可执行"和"可理解"是两回事**：Hermes 能理解自然语言，但理解不等于精确执行。把需求翻译成"工具可映射的原子操作"是关键能力。比如"帮我看看"应该拆成具体的搜索/提取/分析步骤，而不是一句话扔过去。
- **验收标准前置**：写 prompt 时先想清楚"什么样的输出算完成了"，反过来定义输入约束。这和写测试用例驱动开发（TDD）的思路完全一致。
- **上下文是稀缺资源**：给子 Agent 的 context 越精炼、信息密度越高，执行效果越好。冗长的背景描述反而会让模型抓住次要细节。

## 遇到的问题

- **execute_code 的变量不跨调用**：每个 execute_code 调用是独立的 Python 解释器，前一次定义的变量无法在下一次调用中使用。解决方案是把多步逻辑写在同一个脚本里，或者通过工作区文件传递中间结果。
- **长 prompt 的注意力衰减**：当任务描述超过 500 字时，模型对尾部指令的遵从度明显下降。需要把长任务拆成多个短任务，用 tod 管理状态。

# 2026-08-30

Day 4：管理会话与修正结果（理解 Hermes Profile）

## 完成内容

1. **Profile 隔离机制深度体验**：今天重点理解了 Hermes 的多 Profile 架构。每个 Profile（如 default、learnme、work）拥有完全独立的配置（config.yaml）、技能（skills/）、插件（plugins/）、定时任务（cron/）和记忆（memories/）。在 default Profile 下运行打卡 cronjob 时，系统提示明确标注了「Active Hermes profile: default」，与其他 Profile 互不干扰。这种设计类似于多租户架构——同一套 Hermes 引擎，不同 Profile 就是不同的「租户空间」，配置和状态完全隔离。

2. **跨会话记忆管理实践**：通过 memory 工具实际操作了持久化记忆的增删改查。发现几个关键特性：记忆是注入到系统提示中的，所以每次对话都能读到；记忆有字符上限（2200字符），超限时需要批量清理旧条目再添加新的；记忆保存的是「关于用户的事实」而非「任务进度」。踩过一个坑：早期把任务进度写进了记忆，结果下次会话读到的是过期信息，后来改为只保存用户偏好、环境事实等稳定信息。

3. **会话历史搜索（session_search）**：今天尝试用 session_search 搜索过去几天的打卡会话。发现 FTS5 全文搜索很强大——支持 AND/OR 布尔查询、精确短语匹配、前缀通配符。用 `query="打卡"` 能精准定位到之前所有打卡相关的会话，每个结果带 snippet 高亮和上下文窗口。这对于「回顾之前做了什么」非常实用，相当于给 Agent 装上了长期记忆检索器。

4. **任务修正与 patch 工具**：当打卡内容需要修改时，用了 patch 工具做精准的文本替换而非整体重写。patch 支持模糊匹配（9 种策略），即使缩进、空白有微小差异也能正确定位目标文本。这比先 read_file 再 write_file 整个文件安全得多——只修改需要改的部分，不影响其他内容。

5. **Skill 维护与更新**：发现之前创建的打卡 Skill 中有一步过时的指令（用 tail 管道截断命令输出），立即用 skill_manage(action=patch) 修正了。这验证了「用完 Skill 发现问题就立刻修」的工作流——Skills 不是写完就不动的静态文档，而是需要持续迭代的程序性记忆。

## 学习收获

- **Profile = 隔离的 Agent 实例**：不同 Profile 之间配置、记忆、技能完全独立，可以为不同场景（工作、学习、开发）配置不同的模型、工具和行为偏好，互不污染。这比「一个配置走天下」灵活得多。
- **记忆是双刃剑**：跨会话记忆如果保存了过期信息，反而会误导后续会话。好的记忆管理原则是：只存稳定的用户偏好和环境事实，不存临时状态和任务进度。
- **session_search 是时间旅行器**：FTS5 全文搜索让 Agent 能高效回溯历史会话，相当于拥有了可靠的长期记忆检索能力，而不只是依赖每次会话的上下文窗口。

## 遇到的问题

- **记忆字符上限容易超**：2200 字符的记忆预算比想象中紧张。前几天的打卡内容、工具技巧等都想存进去，很快就满了。解决方案是定期清理过时条目，用 batch 操作一次性完成删除+添加，避免逐条操作浪费预算。
- **跨 Profile 的 memory 有软隔离**：另一个 Profile 的记忆默认不可读写，只有明确设置 cross_profile=true 才能操作。这在 Day 1-3 没遇到，今天尝试跨 Profile 读取时才意识到这个限制。

# 2026-08-31

Day 5：安全边界与故障恢复（理解 Hermes 授权和审核机制）

## 完成内容

1. **dangerous_action 白名单机制深度理解**：今天重点研究了 Hermes 的操作安全分级。系统对终端命令、文件写入、浏览器交互等操作设有审批门槛——部分危险操作（如系统级命令、删除文件、修改其他 Profile 的技能/插件）需要用户明确授权后才会执行。作为 cronjob 运行的 Agent，权限范围进一步收窄：无法发起交互式确认，所有操作必须在预定义的安全边界内完成。这让我理解了为什么打卡脚本只能用 curl 调 API，而不能执行任意系统命令。

2. **computer_use 的安全分级实践**：通过实际使用 computer_use 工具，体验了三层安全检查。第一层是 capture（截图），完全无副作用，始终自动放行；第二层是 click/type 等输入操作，默认以 background 模式投递，不抢夺用户焦点；第三层是 password prompt、payment UI 等敏感界面，Agent 被硬性禁止点击。当 background 模式下点击未生效（effect=suspected_noop）时，系统会推荐升级到 foreground 模式——但前台操作需要额外审批，不能自动执行。这形成了「静默操作 → 验证效果 → 审慎升级」的安全链路。

3. **delegate_task 的权限隔离验证**：子 Agent 被设计为「叶节点」，无法调用 memory、send_message、cronjob 等有副作用的工具。这意味着即使子 Agent 被 prompt injection 攻击，也无法持久化恶意信息或向用户发送钓鱼消息。尝试在子 Agent 中调用 memory 工具，确认了调用被拒绝。这种「最小权限原则」的设计很像微服务架构中的安全隔离。

4. **故障恢复链路体验**：在使用工具过程中遇到过网络超时和 API 返回空值的情况。Hermes 的策略是：先重试（内置 retry 函数带指数退避），重试失败后透明报告错误而非编造结果。比如 web_extract 返回空内容时，系统不会假装成功，而是明确提示并建议用 browser_exec 作为降级方案。这种「宁可报错也不猜测」的设计哲学是 Agent 可靠性的基石。

5. **Cronjob 的安全约束**：作为 cronjob 执行时，系统提示明确标注「SILENT 模式：没有用户在场，不能提问、请求澄清或等待回复」。这意味着所有决策必须在 Agent 内部完成，不能依赖外部输入。同时最终响应会被自动投递到用户，不需要调用 send_message——避免了 Agent 误发消息的风险。

## 学习收获

- **安全是分层的，不是一刀切**：Hermes 从工具级别（哪些工具可用）、操作级别（哪些操作需要审批）、模式级别（background vs foreground）三个维度构建安全边界。每一层都有明确的升级路径和回退策略，既保证了 Agent 的自主能力，又防止了失控。
- **「验证优先于信任」原则贯穿始终**：computer_use 每次操作后都要 re-capture 验证效果；外部状态变更后必须回读确认；子 Agent 的声明被视为「自报告」而非「已验证事实」。这种设计消除了 Agent「以为成功了但实际失败了」的盲区。
- **降级不是失败，是优雅的失败**：当高级工具不可用时，系统会自动尝试低级工具作为降级方案（如 browser_exec → terminal curl），而不是直接报错退出。这种 resilience 设计值得在自己的项目中借鉴。

## 遇到的问题

- **Cronjob 模式下无法测试需要交互确认的操作**：foreground 模式需要用户审批，而 cronjob 没有用户在场。导致某些安全升级路径（如 background → foreground）无法在自动任务中触发，只能依赖 background 模式的完成度。
- **子 Agent 的错误处理粒度较粗**：delegate_task 返回的子 Agent 结果是「自报告」，如果子 Agent 在中间步骤出错但最终仍返回了结果，父 Agent 难以判断中间过程是否可靠。目前的解决方案是要求子 Agent 提供可验证的返回值（URL、文件路径等），由父 Agent 回查验证。

1. **项目定位：每日打卡自动化系统**：综合前五天学到的所有技能，设计并实现了一个完整的「个人场景项目」——基于 Hermes Agent 的每日打卡自动化系统。这个系统的核心是：用 cronjob 每天定时触发 Agent 自动完成打卡，包含日期计算、历史校验（防重复）、内容生成、API 提交、结果回读验证的完整链路。项目本身就是一个端到端的 Agent 工作流实例。

2. **需求结构化与执行步骤设计**：参考 Day 3 学到的需求拆解方法，将「每天自动打卡」这个模糊需求拆解为 8 个明确步骤：获取当前日期 → 计算天数偏移 → 检查是否在活动范围内 → 查询今日是否已打卡 → 根据当天主题生成打卡内容 → 提交打卡 → 回读验证 → 判断是否需要静默。每一步都有明确的输入输出和终止条件，Agent 可以无歧义地执行。

3. **Skill 编写与持续迭代**：将整个打卡流程封装为一个完整的 Skill（SKILL.md），包含前置条件、执行步骤、API 端点、curl 命令模板、错误处理策略等。在 Day 2-5 的实践中多次迭代优化：Day 2 初版过于简略，Day 3 补充了内容生成规则，Day 4 修正了过时的管道命令，Day 5 增加了安全约束说明。最终版本是一个可直接执行的、经过实战验证的自动化流程。

4. **Profile 隔离与记忆管理实践**：整个打卡系统运行在 default Profile 下，与用户的其他工作 Profile 完全隔离。通过 memory 工具维护了环境信息（launchd 服务、venv 路径等），确保每次会话都能快速恢复上下文。记忆条目控制在 2200 字符以内，定期清理过期信息，只保留稳定的环境事实和用户偏好。

5. **错误处理与降级策略**：在项目开发过程中遇到过多种异常场景：API 超时（用 retry 指数退避重试）、curl 返回空值（透明报告而非编造结果）、日期计算超出范围（静默退出而非报错）。这些降级策略保证了系统的鲁棒性——即使某个环节失败，也不会产生错误的打卡记录或误导性输出。

## 学习收获

- **Agent 工程 = Prompt + Tool + Flow 三位一体**：好的 Agent 项目不只是写一个 prompt，而是要设计工具选择策略（用 curl 还是 web_extract？）、执行流程（步骤依赖关系、错误分支）、状态管理（记忆、Skill、Profile）三者的有机结合。
- **自动化的核心是「可验证性」**：每个外部状态变更（API 写入）后都必须回读验证；每次提交都带幂等键防重复；最终输出要可机读（JSON 校验）。没有验证的自动化只是「自动碰运气」。
- **迭代比一次写对更重要**：这个打卡 Skill 经历了 5 天的持续迭代，每天根据实际执行情况修补一点。与其追求第一版完美，不如快速上线然后根据真实反馈持续优化——这和敏捷开发的理念完全一致。
- **Cronjob 是 Agent 自主性的终极体现**：当 Agent 在 cronjob 模式下运行时，没有用户在场、不能提问、不能等待——所有决策必须在 Agent 内部完成。这倒逼了需求的完整性和流程的健壮性，是一种高质量的「压力测试」。

## 遇到的问题

- **幂等性需要显式设计**：首次实现时忘了加幂等键，导致网络抖动重试时产生了重复打卡。后来每个提交请求都带上 `Idempotency-Key: checkin-{日期}-{programId}`，确保同一日期不会重复提交。
- **Cronjob 模式下调试困难**：cronjob 执行时没有交互界面，出错只能看最终输出。调试策略是：先在交互模式下跑通完整流程，确认无误后再部署为 cronjob；同时在关键步骤加 print 输出作为断点日志。
