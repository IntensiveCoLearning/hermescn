# 2026-08-27

# HermesCN 残酷共学第1天

**学习时间：** 1小时

## 今日学习

今天以基础概念和规划为主，系统梳理了Hermes Agent的整体结构：模型负责理解、规划、判断和排错，工具负责操作真实系统，Hermes运行时负责组织调用循环，上下文、权限与验收机制共同保证任务可靠完成。工具返回成功并不等于目标达成，还必须通过测试或现实状态回读进行验证。

进一步区分了不同状态和能力的载体：Memory保存少量稳定事实，Skill保存可复用方法，脚本负责确定性动作，数据库保存长期动态状态，Cron负责定时触发，Git负责版本管理，加密备份负责灾难恢复。

学习了Session、Context和任务文档的关系。自动压缩用于控制上下文体积；`/new`、`/resume`和`/branch`用于隔离或延续不同话题；长期复杂任务还需要TASK、STATUS等外部文档保存权威目标和当前状态，不能只依赖聊天记忆。

在安全方面，明确了Key应存入`.env`，不能发送到聊天、写入代码、提交Git、打印日志或进入明文备份；还需要最小权限、按需注入、定期轮换和泄露即撤销。

今天最深刻的收获是系统化排错。无论传统手工排错还是AI辅助排错，底层逻辑都不变：先控制影响、收集证据、判断故障层，再提出可证伪假设，通过最小探针逐一验证；确认根因后实施单一修复，最后使用原始复现、回归测试和现实状态回读验收。AI可以提高采集和分析效率，但不能代替证据。

## 今日产物

完成专题笔记《AI时代的系统化排错：以Hermes Agent为例》，整理了Hermes手工排错方式、不变的排错逻辑、AI原生排错架构，以及AI、工具和人的角色分工。

## 学习感受

还要体系化学习细节，否则在AI的道路上无法走远。

## 下一步

继续学习Hermes的Tools与Skills，重点理解工具调用如何进入真实系统、Skill如何沉淀可复用流程，以及怎样验证Agent确实完成了任务。

# 2026-08-28

# HermesCN 残酷共学第2天

**学习时间：** 1小时

## 今日学习

今天从Telegram语音识别问题出发，梳理了语音消息从Gateway接收、STT转写到大模型理解和回答的完整链路，明确STT是“耳朵”、聊天模型是“大脑”，上游转写错误会直接影响后续推理。

通过真实测试，将STT语言从英语修正为中文`zh`，并把本地`faster-whisper`从`base`升级到`small`。短中文语音的识别准确率明显改善。考虑到VPS只有约1GB内存且只是偶尔使用语音，将模型设置为空闲120秒后卸载，以平衡准确率和资源占用。

进一步分析了Gemini 3.5 Transcribe云端方案，区分了Google AI Pro会员、Gemini应用和Developer API；确认Hermes目前需要通过Transcription Provider插件或命令包装器增加适配层。云端方案能降低VPS资源压力，但需要综合考虑API费用、网络延迟和音频隐私，后续应使用同一批中文、专业术语和中英文混合音频进行A/B测试。

还学习了图片输入、Subagent和Profiles：视觉模型可直接理解图片，文本模型则由辅助视觉模型生成描述；父Agent负责拆解、委派和验收，Subagent在独立上下文中处理任务；Profile用于长期隔离不同Agent的配置、记忆、Session、Skills、凭据和自动化状态，但不等同于操作系统安全沙箱。

## 学习感受

今天主要的感受是，要理清模型、工具、Skills以及各组件之间的关系，才能充分发挥不同板块各自的价值，并让它们协同完成可靠的任务。

## 下一步

继续用长句、网络术语、中英文混合和数字内容测试本地STT；在真实任务中练习由主Agent规划、Subagent独立审查、主Agent统一验收的多Agent工作流。

# 2026-08-29

# HermesCN 残酷共学第3天

**学习时间：** 2小时

## 今日学习

今天重点学习了复杂 Agent 任务的规划、可靠性与验收。明确任务契约应包含目标、输入、输出、范围、约束、失败行为和验收标准；简单任务不必增加仪式感，复杂和高风险任务才使用 L2/L3 契约与质量门禁。工具、HTTP 或 Cron 返回成功只证明某一步执行过，最终仍要检查真实产物和外部状态。

结合个人 AI 日报进行了完整实践：定位候选脚本在 Cron 环境中的导入故障，以及模型通过网页检索补救后掩盖前置失败的问题；修复生产入口，增加信源健康状态、上游日期与状态门禁、HTTP(S) 协议限制和响应大小保护，并扩展异常场景测试。还定位了多个模型 Agent 同时运行导致低内存 VPS 发生 OOM，将 Cron 和 Subagent 并发上限都设为 1，并把日报任务错峰执行，最终通过当天真实任务验证。

进一步配置并验证了模型自动回退链：主模型不可用时先尝试支持工具调用的 OpenRouter 免费模型，再由 DeepSeek 兜底。通过实际 API 工具调用确认免费模型能够返回 `tool_calls`，理解了会话切换、全局默认、Cron 模型选择与自动回退之间的区别。

在多 Agent 架构方面，修正了早期“由 Hermes 统一调度所有任务”的设想，确定每个 Agent 独立管理自己的任务，GitHub只承担跨 Agent 的共享背景、决策、交接和知识候选，Obsidian负责最终知识沉淀。GitHub Actions被定位为服务器端质量门禁，而不是 Agent 调度器。今天已形成专题笔记和详细实施计划，但尚未创建共享仓库或正式接入其他 Agent。
