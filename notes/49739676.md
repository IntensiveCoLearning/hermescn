- Session 上下文只是当前任务的工作记忆；完整历史可进入状态数据库并按需检索。
- 上下文压缩不等于删除历史，也不能替代项目的权威状态文件。

### 2. 理解 Telegram Session 与 Hermes 项目的关系

- Hermes 项目主要通过工作目录及项目上下文文件识别，不是 Telegram 中可以直接切换的独立项目对象。

1. **Memory、Session 和项目文件解决的是不同问题。**

盘点现有自动化后，确认逐项发送成功消息会造成通知噪音，因此实施了两层通知模型：

- 新失败由轻量级 Watchdog 每10分钟检查并即时告警。

汇总和 Watchdog 均使用确定性本地脚本，不调用模型，以降低低内存 VPS 的资源和 Token 开销。健康判断不仅检查调度状态和退出码，也识别业务输出中的失败及数据源降级。

### 3. 理解 Topic、Session 与 Profile 的边界

结合当前 Telegram 使用方式，明确了三层隔离：

- **Topic**：用于划分学习、工作、家庭、Hermes 系统建设和自动化通知等长期领域。
- **Session**：用于隔离某个阶段的具体对话；任务阶段结束或旧上下文产生干扰时，可以在原 Topic 内新建 Session。
- **Profile**：用于隔离长期身份、Memory、Skills、凭据、配置和自动化任务。

Topic 适合上下文整理，但不等于权限、文件和凭据隔离。敏感工作内容仍应留在独立工作环境中，Hermes 只接收脱敏后的背景或结论。

### 4. 统一 Hermes 长期输出目录

检查并迁移了旧的独立笔记机制：

- 将旧知识库中的8份实质文档迁移到 Personal AI OS 的 Hermes `outputs/` 目录。
- 停用并删除旧的独立同步脚本和 systemd Timer。
- 旧仓库改为归档状态，不再作为写入目标或恢复依赖。
- 更新恢复说明、稳定记忆和实例状态，取消旧目录的默认保存策略。
- 明确以后长期保留的笔记、报告和方案统一进入 `outputs/`；项目工作目录继续使用 `projects/`。

迁移过程中发现同步脚本不能正确处理中文文件名，原因是 Git 转义后的路径被误判为越权路径。随后改用 NUL 分隔的原始路径输出，并增加中文文件名回归测试。

## 我的理解

1. **MVP 不是功能简陋，而是验证核心假设的最短闭环。**  
   应先定义边界，完成可运行、可验证、失败时会停止的最小系统，再根据真实需求增加 Candidate、人工审阅和自动化。

2. **模型生成了正确结果，不代表整条自动化链路正常。**  
   调度、脚本、业务输出、远端状态和消息投递必须分别验证，不能只看最终文本或退出码。

3. **集中通知不等于集中任务管理。**  
   可以统一汇总运行状态和异常入口，同时继续保持每个 Agent 的任务自治。

4. **Topic、Session 和 Profile 解决的是不同问题。**  
   Topic 管长期领域，Session 管阶段性上下文，Profile 才负责更强的身份、状态和权限边界。

5. **统一存储位置可以减少重复同步和恢复复杂度。**  
   同一类长期产出不应维护两套目录、两套 Git 同步和两套恢复规则。

## 遇到的问题

- 多个定时任务分别发送成功通知，消息噪音较大，也难以快速判断整体健康状态。  
  **解决：** 改为“异常即时告警 + 例行结果日度汇总”，并进行幂等去重。

- Telegram 投递如果没有明确指定 Topic，消息可能进入私聊根路由，而不是预期的通知 Topic。  
  **解决：** 通知任务显式配置目标 Topic，并将 Topic 视为投递位置而不是 Session 或调度器。

- 旧笔记目录与 Personal AI OS 的输出目录重复，增加同步、恢复和长期维护成本。  
  **解决：** 迁移文档、归档旧仓库、停用旧 Timer，并统一长期输出规则。

- Git 对中文路径的转义导致同步脚本误判越权路径。  
  **解决：** 使用 NUL 分隔的原始路径输出，并补充中文文件名回归测试。

- “Cron 已配置”不等于首次自然调度和实际投递已经成功。  
  **当前状态：** 每日汇总脚本已手动验证，但首次07:00自然运行及实际 Topic 投递仍待回读验收，没有提前标记为成功。
