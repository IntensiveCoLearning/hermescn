## 今日完成

### 1. 理清 Hermes 的多层记忆与状态体系

- Hermes 不只有“全局记忆”和“会话记忆”，还包括 Profile 级长期记忆、项目级上下文、当前 Session、历史 Session 检索、Skills，以及文件、数据库和 Git 等外部状态。
- `USER.md`、`MEMORY.md` 适合保存当前 Profile 中短小、稳定、需要跨 Session 保留的信息，不适合作为完整项目状态库。
- Session 上下文只是当前任务的工作记忆；完整历史可进入状态数据库并按需检索。
- 上下文压缩不等于删除历史，也不能替代项目的权威状态文件。

### 2. 理解 Telegram Session 与 Hermes 项目的关系

- Hermes 项目主要通过工作目录及项目上下文文件识别，不是 Telegram 中可以直接切换的独立项目对象。
- `/new` 只会新建对话 Session，不会自动切换项目目录。
- Hermes 会识别 `AGENTS.md`、`.hermes.md`、`CLAUDE.md` 等项目入口，但不会自动读取目录里的所有普通文档。

### 3. 明确项目级文档的职责分工

- `AGENTS.md`：自动项目入口、稳定规则、恢复流程和文件索引。
- `PROJECT.md`：稳定目标、范围、边界和完成标准。
- `HANDOFF.md`：当前阶段、阻塞、仍有效的决定和下一步。
- `learning-log.md`：按日期保存实际学习、操作、证据和打卡状态。
- 交接文档只保留恢复工作所需的最小动态状态，详细历史进入学习日志，避免重复、冲突和上下文持续膨胀。

### 4. 实际整理共学项目的状态结构

- 为共学项目新建了 `AGENTS.md`，写入恢复顺序、文件职责、事实记录规则、打卡授权、安全边界和低资源约束。
- 精简并重写了 `HANDOFF.md`，删除与历史学习日志重复的内容。
- 保留 `PROJECT.md` 作为稳定项目契约，保留 `learning-log.md` 作为每日事实与证据的权威账本。
- 我已理清记忆分层，尤其是项目级记忆、项目入口和交接文档的职责。

### 5. 对备用模型进行了真实兼容性测试

- 尝试将一级回退模型更换为另一款免费模型，但 Hermes 调用出现长时间超时，直接调用还出现服务端点异常。
- 随后重新测试原一级回退模型：连续3次直接调用全部成功，并完成一次 Hermes Agent 兼容性调用。
- 最终根据实测结果恢复原回退链，并通过配置查询确认生效。

## 我的理解

1. **Memory、Session 和项目文件解决的是不同问题。**  
   Memory 保存稳定的跨会话事实，Session 保存当前任务上下文，项目文档保存可审查、可交接的权威状态，三者不能互相替代。

2. **项目级记忆不是把所有历史塞进一个文件。**  
   更合理的设计是分离稳定目标、动态交接和详细证据，并通过一个精简入口告诉 Agent 应按什么顺序恢复上下文。

3. **自动加载的文件也有 Token 成本。**  
   `AGENTS.md` 应保持短小稳定，不应复制完整项目计划或每日进度；频繁变化的内容应放在交接文件和学习日志中。

4. **模型可用性不能只依据网络评价或配置成功判断。**  
   至少要验证服务端点、连续调用和 Hermes Agent 实际兼容性；配置写入成功不等于备用链路真正可用。

5. **复杂任务应先明确权威状态和文档职责，再进入实现。**  
   这样可以降低跨 Session 恢复时的重复检索、状态冲突和上下文膨胀。

## 遇到的问题

1. **共学项目原先缺少自动项目入口。**  
   处理过程：核实没有适用的项目上下文入口后，新建 `AGENTS.md`，并建立恢复顺序和文件索引。

2. **交接文档与学习日志存在内容重复。**  
   处理过程：删除交接文档中的大段历史，只保留当前阶段、阻塞和下一步；详细过程与证据继续由学习日志维护。

3. **容易把 Telegram 新会话误解为新项目。**  
   处理过程：明确 `/new` 只切换 Session，项目仍取决于工作目录和适用的项目上下文入口。

4. **新候选备用模型实际表现不稳定。**  
   处理过程：通过直接调用和 Hermes 调用进行验证；发现超时和端点异常后，与原模型实测结果对比，最终恢复已经验证可用的回退配置。

## 今天学习了什么

今天围绕 Personal AI OS 的真实建设过程，继续学习复杂系统如何从最小可行产品（MVP）开始，而不是一开始就堆叠完整架构。

1. **明确多 Agent 的自治边界**
   - Claude Code、Codex、Hermes 等 Agent 各自负责并管理自己的任务。
   - GitHub 用于按需交换稳定背景、关键决策和交接信息，而不是让 Hermes 统一调度所有 Agent。
   - 当前简化架构以 `agents/`、`shared/`、`contracts/`、`projects/` 为核心，目录和机制随真实需求生长。

2. **理解 Hermes 的会话与消息路由**
   - Telegram Topic 是消息显示与回复入口。
   - Hermes Session 保存对话上下文；同一 Topic 中也可以切换到新的 Session。
   - Cron 在独立后台上下文中执行，再由 `deliver` 决定结果投递到哪个 Telegram Chat 或 Topic。
   - 跨 Topic 的学习内容不会自动进入当前上下文，需要通过历史 Session 检索，并对实时系统状态重新核验。

3. **用真实产物验证最小闭环**
   - Hermes 状态推送能力只允许写入自己的目录，提交前检查路径和敏感信息，无有效变化时不产生空提交，推送后回读远端状态。
   - 公共记忆读取能力以索引为入口，只读取已确认且与主题匹配的信息，避免把候选、日记和临时交接误当成稳定记忆。
   - 两项能力的测试均重新执行并通过。
   - 每日状态同步任务已经配置，但“配置完成”不等于“运行成功”，仍需在首次触发后检查执行状态、Git 回读和消息投递。

## 今天的关键认识

设计系统时，应先完成一个可运行、可验证、边界清楚的最小闭环，再依据真实反馈扩展。过早加入自动策展、统一调度或大量占位结构，会增加理解成本，也会掩盖尚未验证的核心需求。
