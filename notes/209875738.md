06 的六部分任务结构（背景/目标/输入/限制/交付物/验收）最大的价值是把决定权放回正确位置：三个关键区分是背景≠目标、限制必须能改变行动（"请小心"不算限制，"不联网"才算）、交付物≠验收标准。

07 纠正了我一个隐性误解：会话保存和模型上下文是两回事——完整历史都在 SQLite 里，但模型每轮只看到当前窗口。所以"关键限制写进任务里"不是好习惯，是必需品。恢复会话后先问只读问题核对状态，和交接文件冲突时以文件为准。

09 的四位置分工很实用：每次必须知道的事实进 Memory、偶尔找回的讨论用 Session Search、当前状态写交接文件、重复方法做成 Skill。Memory 准入三条——稳定、常用、短小——直接拿来当检查表用。

10 的分层排错表解开了我以前的困惑：为什么"工具执行成功但结果不对"最容易被误判成安装故障然后白白重装。退出码 0、文件存在都不等于业务验收通过，这一条和昨天 Day 1 的"批准动作≠验收结果"正好接上。

# 2026-08-29

HermesCN 共学 Day 3 打卡

官方主题是“将模糊需求转成 Hermes 可理解的执行任务”。昨天通读了 06 的理论框架，今天重点做实操落地和真实案例重构。

拿自己平时最容易随手丢给 Agent 的一类模糊需求做了改写对照：
* 原始需求（模糊）：“帮我调研一下竞品，做个分析。”
* 重构后的六部分任务（可执行）：
  1. 背景：正在评估产品新方向，需要快速摸清同行现状；
  2. 目标：针对指定的 3 家竞品，提炼核心功能、定价模式与用户主要槽点；
  3. 输入：指定官方定价页与 3 篇深度评测链接（不让 Agent 全网乱搜抓无效信息）；
  4. 限制：只读网页、不触碰未公开数据、不脑补缺失的商业数据（没有就标未披露）；
  5. 交付物：一页对比表格 + 关键发现清单；
  6. 验收：表格字段齐全、每条数据均标注来源 URL、不包含主观推测。

体会与心得：
模糊需求表面上省了提需求的时间，但后续会付出巨大的返工、幻觉纠偏和无休止追问成本。把需求结构化不是“教条”，而是把目标、边界与验收标准锁定在执行前。把任务定义清楚，Agent 才能真正跑出确定的生产力。

# 2026-08-30

HermesCN 共学 Day 4 打卡

今天的学习主题是“管理会话与修正结果（理解 Hermes Profile）”，主要涵盖会话生命周期管理与 Profile 多身份隔离机制。

核心收获与认知：
1. 会话持久化与上下文窗口解耦：完整历史进 SQLite 保证可追溯，但模型单轮只看有限窗口。长会话管理遵循“继续 / 压缩 / 新开”判定原则，跨阶段工作优先依托外部交接文件（handoff）承接状态，而非依赖无限延长的对话上下文。
2. Profile 身份隔离边界：Profile 是逻辑与状态层面的完全隔离（配置、凭据、记忆、Skills、Cron 定时任务均独立），适合按场景拆分不同专职 Agent；同时清晰认识到 Profile 并非操作系统沙箱，底层权限仍需通过环境与工具策略严格约束。

实操结合：
日常正是基于独立的 yara profile 运行个人助理，记忆库（Nowledge Mem）与日常执行环境做到了清晰隔离。今天进一步理顺了跨会话状态交付与多 Profile 协作的边界规范。
