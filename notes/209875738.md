概念收获：一句话分清 memory 和 skill——"需要记住什么考虑 memory，按一套方法做事考虑 skill"；把模糊需求变成可执行任务的四问框架（目标/输入/权限/验收），以及 03 里任务说明的六件套（输入、目标、结构、限制、确认点、验收），以后给 Agent 提需求可以直接套。

最触动的两个原则：一是"批准动作 ≠ 验收结果"——权限确认回答能不能做，不回答做得对不对，退出码 0 不代表业务正确；二是审批前五问（接触什么/改变什么/可否恢复/是否出本机/是否碰凭据资金生产），配套的风险分级表很实用。

实操层面我属于提前入场：环境早已跑通，日常走 Telegram 网关协作。今天借课程做了系统性回检：重跑 hermes doctor 核对环境与认证状态、对照官方安装文档复核了 Docker 部署的数据卷行为差异、按 05 的标准自查了自己的凭据管理实践（key 只存本地 .env、不进对话和文档）。另外这两天刚在接入共学平台 API 时做过防提示词注入的基线方案，正好和本阶段的安全主题互相印证。

# 2026-08-28

HermesCN 共学 Day 2 打卡

今天完成第二阶段全部五篇（06 可执行任务说明 / 07 会话与续接 / 08 工具与Toolsets / 09 Memory与Skills / 10 排错与恢复）。

06 的六部分任务结构（背景/目标/输入/限制/交付物/验收）最大的价值是把决定权放回正确位置：三个关键区分是背景≠目标、限制必须能改变行动（"请小心"不算限制，"不联网"才算）、交付物≠验收标准。

07 纠正了我一个隐性误解：会话保存和模型上下文是两回事——完整历史都在 SQLite 里，但模型每轮只看到当前窗口。所以"关键限制写进任务里"不是好习惯，是必需品。恢复会话后先问只读问题核对状态，和交接文件冲突时以文件为准。

09 的四位置分工很实用：每次必须知道的事实进 Memory、偶尔找回的讨论用 Session Search、当前状态写交接文件、重复方法做成 Skill。Memory 准入三条——稳定、常用、短小——直接拿来当检查表用。

10 的分层排错表解开了我以前的困惑：为什么"工具执行成功但结果不对"最容易被误判成安装故障然后白白重装。退出码 0、文件存在都不等于业务验收通过，这一条和昨天 Day 1 的"批准动作≠验收结果"正好接上。

实操体会：这两天用 Agent 代管共学打卡，实际走的正是 06 的流程——先让它汇总要点（交付物一），我人工验收修改后确认（验收标准二），再幂等提交并读回验证。任务说明六件套已经在真实工作里跑起来了。
