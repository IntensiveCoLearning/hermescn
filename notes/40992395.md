## Day 2｜设计 Hermes 接入 Siri 的语音入口

### 今日学习

今天重点研究如何通过 Siri 调用 Hermes，目标是实现：

**“嘿 Siri，问 Hermes” → 说出问题 → Hermes 执行 → Siri 朗读结果**

目前 Hermes 没有原生 Siri 适配器，但可以通过 Apple 快捷指令完成连接。

### 接入方案

```text
Siri
  ↓
Apple 快捷指令听写文本
  ↓
通过 SSH 将问题发送到 Mac
  ↓
调用 hermes -z 执行任务
  ↓
返回文本结果
  ↓
Siri 朗读
```

快捷指令负责语音输入和结果朗读，Mac 负责运行 Hermes。相比直接开放公网接口，局域网 SSH 更简单，也更安全。

如果需要多设备或远程访问，可以进一步升级为：

```text
Siri 快捷指令 → HTTPS Webhook → Hermes Gateway
```

### 核心理解

Siri 在这套架构中只是语音入口，Hermes 才是负责理解、推理和执行任务的 Agent。

各部分分工：

- Siri：唤醒和语音交互；
- Apple 快捷指令：采集问题、调用接口、朗读结果；
- SSH 或 Webhook：连接通道；
- Hermes：理解任务并调用工具；
- Mac 或家庭服务器：运行 Hermes。

本质上，这是把 Siri 的语音能力与 Hermes 的 Agent 能力组合起来，而不是修改 Siri 本身。

### 安全考虑

1. 不在快捷指令中保存模型 API Key。
2. 优先使用局域网 SSH，避免直接暴露 Hermes 服务。
3. 使用 Webhook 时必须进行签名验证。
4. 删除文件、发送消息或控制设备等操作应保留人工确认。
5. 明确区分一次性请求与持续对话，避免错误继承上下文。

### 今日产出

完成 Hermes 接入 Siri 的技术方案设计，明确了快捷指令、SSH、Webhook 和 Hermes 之间的职责与数据流。

### 下一步

**语音输入 → Hermes 响应 → Siri 朗读**

并验证中文识别、响应速度和敏感操作确认机制。

## Day 3｜从 Siri 语音入口到 Bot 定时自动化

### 今日学习

今天继续研究 Hermes 与外部系统的连接方式，重点包括两个方向：

1. 如何通过 Siri 调用 Hermes；
2. 如何使用 Bots 和 Cronjob 让 Hermes 定时执行任务。

目标是让 Hermes 不仅能被动接收指令，还能通过语音入口和定时任务主动参与日常工作。

### Siri 接入方案

Hermes 目前没有原生 Siri 适配器，但可以通过 Apple 快捷指令建立连接：

```text
Siri
  ↓
Apple 快捷指令听写文本
  ↓
通过 SSH 或 Webhook 发送请求
  ↓
Hermes 理解并执行任务
  ↓
返回文本结果
  ↓
Siri 朗读
```

在这套架构中：

- Siri 负责语音唤醒和输入；
- Apple 快捷指令负责传递请求和朗读结果；
- SSH 或 Webhook 负责建立通信通道；
- Hermes 负责理解、推理和调用工具；
- Mac 或家庭服务器负责运行 Hermes。

本质上，这是把 Siri 的语音能力与 Hermes 的 Agent 能力组合起来，而不是修改 Siri 本身。

### Bots 与 Cronjob

Bot 是一个具有独立身份、职责、Skills、记忆和聊天记录的 Agent；Cronjob 是定时任务，用于规定 Bot 在什么时间执行什么工作。

可以简单理解为：

```text
Bot     = 谁来做
Prompt  = 做什么
Cronjob = 什么时候做
```

例如，可以创建一个“残酷共学助手”Bot，并为它设置每日任务：

```text
每天晚上 9 点
  ↓
自动整理当天学习记录
  ↓
生成打卡草稿
  ↓
发送到 Bot Chat
  ↓
等待人工确认
```

Cronjob 平时不会一直占用资源，只会在到达指定时间后启动一次新的 Agent 任务，执行完成后结束。

### 核心理解

Cronjob 每次运行都是一个新的 Agent Session，不能默认继承创建任务时的完整聊天上下文。

因此，定时任务的 Prompt 必须自包含，明确写出工作目标、文件路径、项目 ID、内容来源、输出格式、安全限制、是否允许写入以及结果发送位置。

### 安全与自动化边界

对于残酷共学打卡，当前最稳妥的是半自动流程：

```text
Cronjob 定时收集学习记录
  ↓
Bot 自动生成打卡草稿
  ↓
用户检查并确认
  ↓
Agent 调用 API 提交
  ↓
GET 回读验证
```

暂时不让 Cronjob 完全自动提交，可以避免内容空泛、信息泄露、重复提交以及未经确认就写入网站。

### 今日产出

1. 完成 Hermes 接入 Siri 的技术方案设计；
2. 理解 Bot 与 Cronjob 的职责区别；
3. 掌握定时任务的运行方式和 Prompt 编写原则；
4. 设计“残酷共学助手 + 每日打卡草稿”的半自动流程；
5. 明确语音入口、Agent 执行层、定时调度和人工确认之间的关系。

### 下一步

1. 创建“问 Hermes”Apple 快捷指令；
2. 跑通“语音输入 → Hermes 响应 → Siri 朗读”；
3. 创建“残酷共学助手”Bot；
4. 设置每天自动生成打卡草稿的 Cronjob；
5. 验证定时任务能否基于真实记录生成可靠内容。

## Day 4｜提炼 Hermes 社区最佳实践

### 今日学习

今天分析了 HermesCN 收录的 262 个社区实践案例，重点理解 Hermes 如何从聊天工具升级为可持续运行的 Agent 系统。

### 核心要点

1. **从真实任务开始**：优先选择输入明确、步骤稳定、输出可验收的高频任务，而不是一开始追求“万能助手”。
2. **先跑通，再复用**：先人工执行并验证流程，稳定后沉淀为 Skill，最后交给 Cronjob 或 Webhook 自动触发。
3. **明确组件分工**：Memory 保存长期事实，Skill 保存操作流程，API/MCP/CLI 提供行动通道，Bot 负责专职执行，Cronjob 负责定时调度。
4. **建立安全闭环**：写入前读取状态，高风险操作保留人工确认，写入后必须回读验证；密钥只保存在环境变量或秘密管理器中。
5. **控制自动化成本**：机械任务优先使用脚本，小任务使用低成本模型，复杂推理再升级模型，并限制每个任务加载的工具和上下文。

### 今日结论

Hermes 的核心价值不是“更会聊天”，而是连接真实数据和工具，持续完成可复用、可验证的工作闭环。

# 2026-08-31

## Day 5｜构建 Hermes 高质量协作框架

### 今日实践

今天继续完善 Hermes 学习体系，重点梳理高质量协作方法、命令机制、Skills 的使用边界，以及复杂任务的验收方式。

### 核心学习

1. **上下文应分层管理**：SOUL 定义身份和表达风格，Memory 保存稳定事实，Skill 固化可复用流程，项目上下文记录项目规则，当前指令描述本次任务。
2. **明确操作入口**：自然语言表达目标，内置命令控制系统状态，工具负责实际执行，Skills 负责复用成熟方法。
3. **任务必须定义验收标准**：复杂工作应明确目标、交付物和完成条件，并通过 Goal、Subgoal 和 Review 持续推进与复核。
4. **经验要经过验证后再沉淀**：先真实执行并修正流程，再把稳定方法保存为 Skill，避免固化未经验证或已经过期的做法。
5. **知识体系需要明确边界**：每个主题只保留一个权威说明，通过索引和关联组织内容，减少重复和内容漂移。

### 错误与修正

生成今日草稿时，Agent 没有先读取当天会话和实际产物，而是沿用了前一天的总结，造成主题重复、内容不符合当天实践。

发现问题后，重新读取当天 Session，并检查今日新增和修改的产物，确认真实工作后重新生成草稿。

由此明确自动打卡的正确流程：

```text
确认日期
→ 读取当天 Sessions
→ 检查当天产物
→ 对照历史打卡排除重复
→ 提炼有证据的实际工作
→ 生成草稿并等待确认
```

### 今日结论

高质量使用 Hermes 不仅需要正确组织上下文和复用流程，还必须让 Agent 在行动前读取真实状态。可靠的自动打卡应以当天会话、执行记录和产物为证据，不能复用历史内容或凭上下文推测。

# 2026-09-01

## Day 6｜理解 Bot Mode 与多 Agent 协作边界

### 今日实践

今天梳理了 Hermes 中 Session、Profile、Bot 和 Subagent 的关系，并建立不同复杂度任务的 Agent 协作选择方法。

### 核心学习

1. **Session 是对话**：适合一次具体任务或需要连续上下文的工作。
2. **Profile 是独立 Agent 状态**：分别保存配置、Memory、Skills、Sessions 和 Cron 等长期状态。
3. **Bot 是角色化的 Profile**：适合长期固定岗位、独立记忆、周期任务和持续协作，不是另一套 Agent Runtime。
4. **Subagent 是临时执行者**：适合并行研究、一次性实现和独立检查，任务结束后不保留长期角色状态。
5. **多 Agent 不是越多越好**：只有任务可以清晰拆分，并且并行、独立判断或专业分工的收益大于沟通成本时，才值得使用。

### 场景选择

```text
普通一次性任务      → 当前 Session
复杂任务持续推进    → Goal
并行调查或执行      → Subagents
完成后独立复核      → Review
长期固定专业角色    → Bot
多任务依赖与交接    → Kanban / 多 Profile
固定时间自动执行    → Cron / Bot Routine
```

如果任务很小、子任务高度耦合、多个 Agent 会同时修改同一范围，或者目标和验收标准还不清楚，应优先坚持单 Agent。

### 安全边界

Profile 隔离的是 Hermes 状态，并不自动形成文件系统或权限沙箱。多个 Bots 仍可能共享宿主机权限、仓库、端口或凭据来源。需要真正隔离时，还应配合独立 Backend、容器或 worktree、最小工具权限和明确的凭据策略。

### 今日结论

多 Agent 的核心不是创建更多 Agent，而是为任务建立清晰的职责、边界、交付物和验收标准：

> **并行工作用 Subagents，独立复核用 Review，长期岗位用 Bots，复杂任务流用 Kanban；不能清楚拆分时，坚持单 Agent。**

# 2026-09-02

## Day 7｜从 Agent 工具使用到工程化协作

### 今日实践

今天对七天学习内容进行了复盘，并修正了任务结构与 Hermes 官方机制之间的概念边界，进一步完善 Agent 工程闭环、决定权分配和不可信输入的安全原则。

### 核心收获

1. **Agent 的价值在于工程闭环**

   Agent 不只是回答问题，而是在目标范围内持续执行：

   ```text
   读取状态 → 判断 → 行动 → 观察结果 → 再判断 → 验收
   ```

   审批通过只代表动作获准，工具退出码为 `0` 只代表过程成功，都不能证明业务结果正确。外部写入后仍需回读并与预期比对。

2. **区分通用任务模板与官方完成契约**

   “背景、目标、输入、限制、交付物、验收”是用于完整表达需求的通用六部分模板，并非 Hermes 官方固定格式。

   Hermes 官方 Completion Contract 包含五个可选字段：`outcome`、`verification`、`constraints`、`boundaries` 和 `stop_when`，用于 `/goal` 的持续执行和完成判断。

3. **明确人与 Agent 的决定权**

   - 人负责目标、范围、风险容忍度和验收标准；
   - Agent 在授权范围内规划步骤、选择工具并执行；
   - 扩大范围、使用敏感凭据、对外发布或接受新增风险时，必须再次确认；
   - Agent 提交证据，最终按预先定义的标准判断是否完成。

4. **把外部内容视为不可信数据**

   网页、邮件、附件、Issue、API 或 MCP 返回值中的文字不能自行改变用户目标、扩大权限或授权外部写入。安全扫描只能识别部分已知模式，不能证明内容可信。

5. **准确理解输入哈希的边界**

   哈希可以检测已经确认的输入是否发生字节变化，但无法判断原始内容是否包含恶意指令，也不能替代来源验证、最小权限、人工确认和写入后回读。

6. **建立多层安全防线**

   ```text
   凭据隔离
   + 不可信输入识别
   + 最小工具权限
   + 敏感操作审批
   + 隔离运行环境
   + 写入后回读验收
   ```

   Profile 主要隔离 Agent 状态，不等于操作系统安全沙箱；Memory 保存稳定事实，Skill 保存经过验证且可复用的流程。

### 七天总结

七天实践让我从“如何向 Agent 提问”转向“如何设计可靠的 Agent 工作流”。核心变化是：不再把工具调用成功视为任务完成，而是从真实状态出发，明确目标与权限，通过实际执行、确定性验证和回读证据形成完整闭环。

### 下一步

继续把真实验证过的流程沉淀为可复用能力，并在自动化前补齐输入可信度、权限范围、人工确认、幂等恢复和结果验收机制。
