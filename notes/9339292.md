# 2026-08-27

**与 OpenClaw 记忆系统的关键对比：**

OpenClaw 也有内置记忆——它使用 `MEMORY.md` 存储长期事实，使用按日期的每日笔记存储会话上下文，都基于纯文本文件。但它存在两个局限：

* **记忆写入完全依赖模型主动判断**：模型决定什么值得保存，没有额外机制确保真正重要的内容被记住。在短会话或任务导向的对话中，Agent 可能什么都不写。
* **每日笔记只自动加载最近两天**：上周的笔记虽然在磁盘上且可通过 SQLite 向量索引搜索，但 Agent 需要主动知道该去搜索、在正确的时间用正确的查询词。实际运行中它并不总是能做到这一点。

Hermes 的三层记忆设计从根本上解决了这些问题：

**第一层：上下文压缩（Context Compression）**

这是一种类似“工作记忆”的机制，用于管理短时上下文。每次会话的推理过程都在这一层进行，但会话结束后不会保留。它的作用是让 Agent 在当前任务中保持连贯，而非长期存储。

**第二层：SQLite FTS5 会话搜索（SQLite FTS5 Session Search）**

这一层负责检索历史会话的“冷存储”。所有 CLI 和消息渠道的会话记录都存入 SQLite 数据库，Agent 可以通过 `session_search` 工具主动检索——“我们上周讨论过认证服务吗？”这种跨会话的 episodic recall 完全依赖这一层。

**第三层：持久化的 MEMORY.md（Persistent MEMORY.md）**

这一层存储跨会话的核心事实与知识，类似人脑中的海马体，负责将重要信息固化为长期记忆。`MEMORY.md`（约 2,200 字符）存储持久事实，`USER.md`（约 1,375 字符）存储用户画像。两者在每次会话开始时作为“冻结快照”加载到上下文中，确保 Agent 始终知道你告诉过它的关键信息。

更重要的是，Hermes 内置了 **“提醒间隔”（nudge\_interval）机制**——在会话运行的固定间隔里，Agent 会收到一条内部系统提示，主动复盘当前会话中值得保存的内容，不需要用户插手。

可以说，OpenClaw 的记忆系统是“被动响应式”的，而 Hermes 的记忆系统是“主动构建式”的。

**补充 1**：

Hermes 官方文档明确写道：`MEMORY.md` 有 2,200 字符的限制，`USER.md` 有 1,375 字符的限制。这个设计不是随意设定的，而是为了实现一个核心理念，**"记忆策展"（memory curation）**：

* **强制精炼，防止污染**：如果不设限，Agent 会把大量琐碎信息塞进去，导致上下文臃肿，真正重要的信息反而被淹没。限制强制 Agent 只记录最重要的东西，避免记忆库变成信息垃圾堆。
* **优化 Token 成本**：这两个文件每次会话开始时都会完整注入到系统提示词中。如果文件无限制膨胀，每次调用的 Token 成本都会线性增长。2,200 + 1,375 = 3,575 字符，换算下来大约是 1,300 个 token，这个数量足够容纳 15-20 条有效记录，同时不会显著占用上下文窗口。
* **跨模型兼容**：使用字符数而非 Token 数作为限制单位，可以确保在不同模型（tokenizer 差异很大）之间切换时，记忆行为保持一致。
* **安全防护**：记忆条目在写入前会经过安全扫描，匹配到提示注入、凭证泄露、SSH 后门等威胁模式的内容会被直接阻止。这很重要，因为这些记忆会被注入系统提示词，如果不加过滤，恶意内容相当于获得了对 Agent 的"最高权限"。

官方文档中还提到一个有趣的设计细节：**系统提示词里会显示当前记忆的使用百分比**（如 `[67% — 1,474/2,200 chars]`），让 Agent 自己知道还剩多少空间，从而自主决定是否需要整理、合并或删除内容。

**补充 2：**

我发现国内很多的自媒体会将 Hermes 描述为“四层记忆系统”，是因为他们将独立的“技能系统”作为“程序性记忆层”纳入了广义的记忆体系。这种解读并不是官方的标准说法，但确实便于理解技能系统的核心价值，它是 Agent “自进化”能力的关键载体，。

技能系统在官方架构中是一个独立的子系统，与三层记忆系统并列。官方文档将技能定义为 Agent 的 **“过程性记忆”** ，每个 Skill 捕获的不是一般性事实，而是针对特定类型任务的、经过验证的可复用步骤。

# 2026-08-28

## &#x20;**双 Agent 协同：Hermes + OpenClaw 最佳实践**

再次强调，这是一种高阶玩法，对于绝大多数普通用户或者单一场景的应用，单独使用 Hermess 就足够了。它们两个确实不是二选一的关系。两者的设计哲学决定了它们天然互补：**Hermes 向内求深度（学习-记忆-进化），OpenClaw 向外求广度（连接-调度-分发）** 。社区已经催生了专门的桥接工具 `HermesClaw`，打通两者。



![](https://static001.geekbang.org/infoq/dc/dc480b8ef69409719d914f4caa2f49b7.jpeg?x-oss-process=image%2Fresize%2Cp_80%2Fauto-orient%2C1)



**分工建议：**

* **用 OpenClaw 做“手脚”**：连接各种外部工具和渠道。比如接入飞书、调用 Gmail、操作 Notion，这些事情 OpenClaw 最擅长。
* **用 Hermes 做“大脑”**：负责记住你的偏好、学习你的工作习惯、提供有上下文的深度建议。

**关于技能复用：**

* 手动编写的 SKILL.md 文件如果遵循 **agentskills.io** 开放标准，原则上可以在两者之间迁移。
* OpenClaw 依托的 ClawHub 技能市场（超过 13000 个技能插件）依赖 Gateway 的调度机制和 Node 的执行环境，**不能直接**被 Hermes 调用。

**场景示例**：在飞书里 @机器人 说“帮我查一下上周那封关于预算的邮件”：

1. OpenClaw Gateway 收到消息，识别出需要调用 Gmail 技能。
2. OpenClaw 去 Gmail 里检索相关邮件。
3. 同时 OpenClaw 把对话上下文转发给 Hermes，Hermes 从记忆中调出“上周”你讨论过的预算相关内容。
4. 两边结果汇总后，返回一个既包含邮件内容、又结合了历史上下文的完整回复。

**迁移建议**：如果你已经在用 OpenClaw，Hermes 内置了迁移命令 `hermes claw migrate`，可以一键导入配置、API 密钥、对话历史和技能列表。

**中文参考文档**：[https://hermes.xaapi.ai/guide/migration](https://xie.infoq.cn/link?target=https%3A%2F%2Fhermes.xaapi.ai%2Fguide%2Fmigration)
