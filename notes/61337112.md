## 今日主题

熟悉 Hermes 的基础使用：配置管理、Profile 隔离、模型切换与结果验证。

## 今天完成了什么

### 1. 完成 Profile 配置迁移

对 `ai-web3-dev` Profile 执行配置迁移：

```bash
hermes --profile ai-web3-dev config migrate
```

实际结果：

```text
Config version: v26 → v39
```

迁移完成后，通过 `config check` 和 `profile show` 检查配置状态，确认新版本配置已经生效。

### 2. 检查配置迁移产生的变化

迁移器自动调整了部分默认配置，包括：

- 后台任务通知切换为简洁模式
- Subagent 工具调用预算提高
- 并行 Subagent 数量上限提高
- Profile 配置格式升级到最新版本
- Secret redaction 保持启用

同时确认以下内容没有因迁移丢失：

- `SOUL.md` 中的 Tim 学习助手定位
- AI × Web3 与 Go 后端转型目标
- 用户画像与持久 Memory
- 工作区路径与已有 Skills

### 3. 修正并验证模型配置

迁移过程中一度错误地把 Profile 模型设置成了 Kimi。发现后进行了纠正，并清理了遗留的 Kimi `base_url`。

当前配置已经验证为：

```yaml
model:
  default: gpt-5.6-sol
  provider: openai-codex
  base_url: ""
```

最终状态：

```text
Profile: ai-web3-dev
Model: gpt-5.6-sol (openai-codex)
Config version: 39
Skills: 379
SOUL.md: exists
```

## 今天的收获

1. **Profile 是独立运行环境**

   不同 Profile 可以分别维护模型、配置、Memory、Skills 和身份设定，修改时必须明确目标 Profile，不能只看当前 WebUI 使用的模型。

2. **配置迁移后必须重新验证**

   命令成功不代表最终配置一定符合预期。迁移后至少应检查：

   ```text
   config check
   profile show
   model provider
   base_url
   config version
   ```

3. **模型配置由多个字段共同决定**

   切换模型不能只修改模型名，还需要核对：

   - `model.default`
   - `model.provider`
   - `model.base_url`
   - 对应认证信息

   如果残留了其他 Provider 的 `base_url`，请求可能被发送到错误的服务。

4. **用户纠正也是重要的验证信号**

   今天发现模型配置错误后，没有继续基于错误假设操作，而是根据实际目标重新修改并回读配置。Agent 的执行结果仍然需要人工检查，尤其是模型、权限和外部写入等关键配置。

## 当前结果

今天完成了一个完整的 Hermes 配置管理闭环：

```text
发现旧配置
→ 执行迁移
→ 检查迁移结果
→ 发现模型错误
→ 修正 Provider 与模型
→ 清理遗留配置
→ 回读验证最终状态
```

# 2026-08-29

# HermesCN 残酷共学 · Day 3 打卡

## 今日主题

将模糊需求转化为 Hermes 可以理解、执行和验收的工程任务。

## 原始需求

今天最初的需求是：

> 保留 DSH 的 AI-Teacher，同时让 Hermes 也能使用 AI-Teacher 的教学逻辑。

这个描述表达了目标，但缺少实现边界：

- 两套 Agent 是否共用数据
- 教学逻辑由谁维护
- 如何避免重复实现
- DSH 与 Hermes 如何调用
- 如何验证两个系统的行为一致
- 如何防止并发写入覆盖学习记录

## 今天完成了什么

### 1. 阅读现有 AI-Teacher 实现

梳理了当前 DSH AI-Teacher 的主要能力：

```text
teacher_save_note
teacher_log_mastery
teacher_review_plan
teacher_quiz
```

现有数据包括：

```text
mastery.json
quizzes/
Obsidian AI老师笔记/
```

同时确认教学状态、Quiz 和学习笔记不能简单复制成两套，否则 DSH 与 Hermes 会逐渐产生不一致的数据。

### 2. 验证 DSH 的 MCP 接入能力

通过阅读 DSH 文档与源码，确认 DSH 已支持：

- `stdio` MCP Server
- `streamable-http` MCP Server
- MCP 工具自动发现
- 工具命名空间隔离
- 工具调用超时
- 断线重连策略

DSH 会把外部 MCP 工具注册为：

```text
mcp__<serverName>__<tool>
```

这证明“让 DSH 和 Hermes 共同连接一个 AI-Teacher MCP Server”在架构上可行。

### 3. 将模糊需求收敛为目标架构

最终把需求收敛为：

```text
                AI-Teacher MCP Server
                         │
        ┌────────────────┴────────────────┐
        │                                 │
   DSH MCP Client                   Hermes MCP Client
        │                                 │
  保留 DSH 教师体验                 使用 Tim 学习工作流
```

核心原则：

- DSH 的 AI-Teacher 使用体验继续保留
- Hermes 不直接复制 DSH 的 Cordis Plugin
- 四个教学工具抽取为共享 MCP 能力
- 两个 Agent 使用同一套学习状态和笔记
- Tim 的身份继续由 Hermes `SOUL.md` 管理
- DSH 与 Hermes 不重复实现数据存储逻辑

### 4. 形成可执行任务定义

**任务目标：**

实现一个独立的 AI-Teacher MCP Server，同时供 DSH 和 Hermes 调用。

**输入：**

- 现有 DSH AI-Teacher Plugin
- `mastery.json`
- `quizzes/`
- Obsidian AI 老师笔记目录
- DSH MCP Client 配置规范
- Hermes MCP 配置规范

**预期产物：**

```text
ai-teacher-mcp/
├── server
├── storage
├── tests
└── README.md
```

对外提供四个工具：

```text
teacher_save_note
teacher_log_mastery
teacher_review_plan
teacher_quiz
```

**安全与数据约束：**

- 使用 `Asia/Shanghai` 计算复习日期
- 写入使用文件锁和原子替换
- 禁止绝对路径和 `../` 路径穿越
- `BasicRepository` 保持只读
- API Key、Token 和个人数据不得进入公开仓库
- DSH 与 Hermes 不得同时维护两份独立学习状态

**验收标准：**

1. DSH 能发现并调用四个 AI-Teacher MCP 工具。
2. Hermes 能发现并调用同样的四个工具。
3. DSH 写入的掌握度记录可以被 Hermes 读取。
4. Hermes 保存的学习笔记可以被 DSH 使用。
5. 两端看到的 `review plan` 结果一致。
6. 并发写入不会破坏 `mastery.json`。
7. 所有测试使用临时目录，不修改真实学习数据。

## 今日收获

今天最大的收获是：给 Agent 的好任务不能只描述“想要什么”，还必须明确：

```text
目标
→ 输入
→ 边界
→ 执行步骤
→ 产物
→ 验收标准
```

“MCP 是否可行”也不能只靠印象判断，需要通过真实文档、配置类型和源码实现进行验证。

同时明确了一个工程原则：

> 共享业务能力应该抽成公共接口，而不是分别为两个 Agent 复制一套实现。

## 当前进度

今天完成的是：

- 现有实现梳理
- DSH MCP 能力验证
- 共享架构设计
- 风险边界识别
- 可执行任务与验收标准定义

尚未完成：
