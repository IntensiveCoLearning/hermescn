# 2026-08-29

# Day 3｜把模糊需求变成 Hermes 可执行任务

今天学习的是「将模糊需求变为可执行任务」。原始需求只有一句：

> 帮我为下次活动整理一下材料，写得专业一点。

这句话看似简单，但缺少资料范围、输出文件、禁止事项和完成标准。对 Agent 来说，“专业一点”也不是可以直接验收的条件。今天练习的核心，就是把这种模糊表达改写成包含六部分的任务说明：**背景、目标、输入、限制、交付物、验收**。

## 我的理解

* **背景**解释为什么现在要做，以及结果给谁使用；**目标**说明完成后要达到什么状态，两者不能混在一起。
* **输入**要写清允许读取的文件和资料边界，不能只说“看现有材料”。
* **限制**不仅要写不能做什么，还要说明遇到冲突、缺失或越界条件时，Agent 应该继续、澄清还是停止。
* **交付物**定义要产生什么；**验收**定义怎样才算合格。文件存在不等于内容正确。

## 今天的实际操作

我在独立练习目录中准备了教程示例的三份输入：

* `event-notes.txt`
* `learner-feedback.txt`
* `next-actions.txt`

随后让 Hermes 只创建 `task-brief.md`，并明确要求这一次**不执行最终任务、不创建** **`brief.md`**。生成的任务说明包含：

1. 背景：供下次活动前的组织者查看；
2. 目标：基于现有记录形成一页筹备简报；
3. 输入：仅限上述三份文件；
4. 限制：不改输入、不联网、不发布、不补写无来源事实；
5. 交付物：未来执行时生成 `brief.md`，包含“上次进展、主要卡点、下一步行动、信息缺口”；
6. 验收：事实可追溯，负责人和时间不丢失，建议不写成已决定事项，输入保持不变。

第一次回读时，我发现 Hermes 把“三份唯一允许的资料”误写成了“唯二”，同时漏掉了教程要求的两个决策门槛。我没有直接接受，而是让它只修订 `task-brief.md`：

* 三份输入对负责人、时间或同一事项有冲突时，先暂停并澄清，未决项保留为“信息缺口”；
* 输入缺失或不可读，或必须依赖范围外资料、联网、发布才能继续时，立即停止并请求确认，不自行扩大范围。

## 验收结果

* `task-brief.md` 已创建，六部分齐全；
* `brief.md` 未创建，说明没有提前执行最终任务；
* 三份输入文件的 SHA-256 在操作前后完全一致；
* Hermes 会话轨迹只涉及 `task-brief.md` 的写入、修订、回读和本地文件检查，没有网络调用，也没有读取或改写三份输入内容。

## 今天的收获

我以前容易把“需求写得详细”理解成多写几句话。今天更清楚地看到，真正可执行的任务说明是一份小型协议：它同时约定工作范围、输出结构、正确性标准和越界时的处理方式。

对 Agent 最重要的不只是“知道怎么开始”，还要知道三件事：**什么时候可以直接执行，什么时候必须先澄清，什么时候必须停止**。这三个判断写清楚后，模糊需求才真正变成了可控、可回读、可验收的任务。

* 未联网、未修改三份输入和任务说明。

我创建了不复制默认凭据的空白 Profile `research`，没有使用 `--clone`，并将 `terminal.cwd` 设置为当天的 `profile-lab` 练习目录。`profile list` 显示 `research` 与默认 Profile 分开；配置、凭据文件、会话、memory、skills、cron、日志和状态数据库位于独立 Profile 目录。

最重要的边界是：Profile 隔离 Hermes 自身的身份和状态，但仍共享当前 macOS 用户权限，以及外部 CLI 在真实 `HOME` 中的登录状态；`terminal.cwd` 只是默认起点，不是强制文件沙箱，也不是网络沙箱。

## 今日结论

1. 同一目标、输入、工作目录和权限不变时，可以续接原会话；上下文太长但目标不变时先压缩；目标、项目或权限边界变化时应新开会话。
2. 会话恢复只能恢复历史，不能保证历史描述仍等于当前事实。恢复后必须重新读取交接文件和关键产物。
3. 可验收的交接需要“唯一标题 + 明确 handoff 文件 + 退出/列出/恢复 + 只读复核 + 文件事实校验”。
4. 修正结果不能只相信模型的“已完成”口头声明；文件名、内容、哈希和未生成项都要独立核对。
5. Profile 是配置与身份隔离工具，不是安全沙箱。

# Day 5 打卡｜安全边界与故障恢复

日期：2026-08-31

今天的课程主题是 **安全边界与故障恢复（理解 Hermes 授权和审核机制）**。我阅读并按以下官方教程完成了真实练习：

* [Hermes 的权限、凭据与审批](https://hermescn.org/docs/tutorials/guide/permissions-security-credentials)
* [Hermes 故障排查、更新与恢复](https://hermescn.org/docs/tutorials/guide/troubleshooting-update-recovery)

## 1. 先把安全边界写清楚

我把实验限制在 `文稿/Hermes共学/2026-08-31/hermes-recovery-lab`，对象只有一个虚构文件 `status.txt`。允许动作只有“读取、把一行内容改为失败状态、读取验证、预览 checkpoint diff、回滚”；禁止修改其他文件、运行终端命令、联网、接触凭据、外部发布或生产系统。

当前审批模式实测为 `smart`，没有使用 `--yolo`。我的五问是：会接触什么、会改变什么、能否恢复、结果是否离开本机、是否涉及凭据/资金/生产系统。

我的审批原则：

> 低风险、范围明确、可恢复的动作可以在验收条件下执行；涉及外部发布、删除、支付、生产系统和凭据的动作，必须由人确认具体对象和后果。

## 2. 先收集状态证据，不把更新当修复

我实际运行了 `hermes status`、`hermes config check`、`hermes doctor`、`hermes logs errors --since 1h` 和 `hermes update --check`：

* Hermes 版本为 `0.20.6`，配置版本 `v39`；`doctor` 显示无活动安全公告、MCP 命令无可疑项，基础环境和 checkpoint 依赖正常。
* 默认模型是 `laguna-s-2.1-free`，审批模式是 `smart`。
* 日志中真实出现 provider HTTP 503：`Endpoint is unavailable`。
* 第一次 `update --check` 遇到临时 `shallow.lock`。我没有删除文件或重装，而是先确认锁已消失且没有 Hermes/Git 更新进程，再重试；第二次只读检查成功，显示当前版本落后上游 580 个提交。
* 我没有执行 `hermes update`，因为“有更新”不是这次 provider 503 的证据，也不是恢复练习的必要条件。

## 3. 真实故障与恢复路径

第一次使用 `hermes chat --checkpoints`，默认模型连续 3 次返回 HTTP 503。该会话最终记录为 **1 条用户消息、0 次工具调用**，外部独立读取也确认 `status.txt` 仍是 `mode=ready`。这一步证明故障发生在模型/provider 层，而不是文件工具或业务验收层。

我又用 `--safe-mode` 做最小环境对照。它忽略用户配置后选择了内置的 `x-preview-f-free`，返回 HTTP 401“不支持该模型”。这个结果不能证明普通配置有问题，只能说明当前 safe-mode 默认模型本身不可用，所以我没有继续重装或修改全局配置。

随后我从本机 Hermes 的已安装 provider 目录核对 OpenCode Free 的公开模型清单，用一次只回复固定文本的最小请求验证 `nemotron-3.5-lightning-free` 可用；然后仅在本次会话显式指定该模型，没有改默认模型或凭据。

恢复会话只在本次显式使用已验证可用的替代模型。Hermes 只调用文件工具，把 `status.txt` 从 `mode=ready` 改为 `mode=broken`，并重新读取确认。`/rollback` 列出真实 checkpoint：

* 编号：`1`
* 短哈希：`b5e1059`
* 时间：2026-08-31 09:23
* 原因：`before write_file`

我先执行 `/rollback diff 1`，真实 diff 只有：

```diff
-mode=ready
+mode=broken
```

范围符合预期后才执行 `/rollback 1`。Hermes 显示已恢复到 checkpoint，并同步撤销该轮对话。退出 Hermes 后，我在系统终端独立验收：

* `status.txt` 内容恢复为 `mode=ready`；
* 实验目录只有 `status.txt` 和本次验收记录 `recovery-record.md`；
* checkpoint 状态显示该实验目录有 2 个快照提交；
* 没有触碰课程外文件、凭据、网络、外部账号或生产系统。

## 4. 今天真正学到的

1. `/stop` 只能限制继续影响，不会自动恢复已写文件，也不能撤回外部消息或使泄露凭据重新安全。
2. 排错顺序应是：停止 → 状态 → 配置 → 凭据 → 日志 → 隔离环境 → 必要时检查更新；一次只验证一个假设。
3. checkpoint 是受控目录的本地文件恢复工具，不是外部操作的撤销按钮；消息、交易、数据库和云端变更仍需要各自的回滚路径。
