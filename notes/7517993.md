# 2026-08-27

# Hermes 残酷共学｜如何选择最适合自己的 Hermes 打开方式

Hermes 安装只需要一行命令，但是对于 Hermes 来说，使用的方式有 N 种 ，可以通过最适合自己的方式来使用 Hermes。

就拿我实际在用的环境举例。现在用来 Hermes 共学的这个跑在云服务器上，通过网关接进 Telegram 群聊。同一台服务器上，我也可以开终端用 TUI 跟它对话，出门在外可以通过手机上的 Telegram 找它。

另外我在自己的 Mac 上页安装了 Hermes，这个 Hermes 主要用来做开发，因为  Mac 上开发移动端和桌面端程序更加方便，梳理完成开发的需求和工作之后，可以使用  /goal 来触发 Hermes 进行 E2E 测试，自己将所有的功能调试完成，期间不需要人为干扰。

在开始使用 Hermes 之前，有一些基础的概念需要理解。

## Hermes 中 Session、Project、Profile 各是什么

Session 是一次对话。不管从哪个入口发起的，CLI、Telegram、Discord 还是定时任务，每次对话都是一条 session，记在 `state.db` 里。会话可以恢复、重命名、搜索、按平台过滤，也可以使用 `hermes --resume` 恢复 session。

Project 是一个工作目录。你在哪个目录里启动 Hermes，它就按哪个项目干活，自动加载项目根目录里的 AGENTS.md 或 HERMES.md，里面写的是这个项目的结构和约定。

Profile 是一整套独立的 Hermes 配置。一个 profile 拥有自己完整的配置、密钥、记忆、技能、会话和定时任务，相当于同一台机器上启动了多个 Hermes。最近 Hermes 推出的 Bot Mode 本质上就是让每个 Bot 拥有一个独立的 Profile。这个也是后续 Agent 使用的趋势。


## Hermes 的打开方式

Hermes 支持多种打开方式。

最简单的方式是直接在命令行打开，但这种方式目前已经不推荐是使用了。
```shell
hermes
```

![Pasted image 20260826221852.png](https://raw.githubusercontent.com/rayjun/hermescn-assets/main/Pasted%20image%2020260826221852.png)


如果想在命令行使用，可以使用 tui 使用，官方现在推荐用 TUI 跑交互式对话，它比老的命令行模式更好用。
```shell
hermes --tui
```

![Pasted image 20260826222039.png](https://raw.githubusercontent.com/rayjun/hermescn-assets/main/Pasted%20image%2020260826222039.png)


对于很多没有技术背景的同学，可以直接从 https://hermes-agent.nousresearch.com/desktop 下载桌面端程序。或者通过终端进行安装，然后就有了一个桌面端的 Hermes，这种方式比较适合没有技术背景的同学使用
```shell
hermes desktop
```

![Pasted image 20260826222748.png](https://raw.githubusercontent.com/rayjun/hermescn-assets/main/Pasted%20image%2020260826222748.png)


除了上面几种方式，Hermes 最灵活的方式就是通过网关进行配置，可以把 Hermes 接入到主流的聊天工具中，然后用户可以通过聊天工具来使用 Hermes。基本上支持了当前主流的聊天工具。

![Clipboard_Screenshot_1787754757.png](https://raw.githubusercontent.com/rayjun/hermescn-assets/main/Clipboard_Screenshot_1787754757.png)


当前比较受欢迎的是 Telegram + Hermes 组合。可以参考 Bruce 的 Telegram + Hermes 的配置方式：https://x.com/brucexu_eth/status/2091455215367250367


另外移动端的 Hermes 官方说已经在开发中了，但是估计还需要时间才能发布。

## Hermes 怎么使用 LLM 服务

Hermes 本身只是一个 Agent，本身不提供 LLM 服务，但是官方提供了 Nous Portal 中转站，可以直接连接到 Hermes 上。

除了 Nous Portal，Hermes 几乎支持当前主流的 LLM 服务。这些服务统称 provider，OpenRouter、Anthropic、OpenAI、Google Gemini、DeepSeek、xAI、Kimi、通义千问这些主流厂商都在列，国内和海外的 API 服务基本全覆盖。

![Pasted image 20260826224346.png](https://raw.githubusercontent.com/rayjun/hermescn-assets/main/Pasted%20image%2020260826224346.png)


换模型的入口有两个。装好之后想定默认模型，跑 `hermes model`，交互式选择 provider 和模型。对话中途想换，在 TUI 或聊天软件里发 `/model`，部分界面支持直接写 `provider:模型名` 的格式，连菜单都不用翻。每个会话的模型选择是独立的，互不干扰。

本地模型也能接。电脑上跑着 Ollama 或者 vLLM 这类服务，它们都提供 OpenAI 兼容的接口，在配置里填本地地址和端口就行。好处是数据不出机器，坏处是本地模型对机器要求高。

## 通过 Tailscale 来组织一个 Hermes 网络

因为跨机器的两个 Hermes 互不相通，会话不会自动同步。机器多了以后，就很难管理。每台服务器都有自己的地址，有的在内网，有的在云上，端口还得一个一个转发，管理起来很烦。

我的做法是用 Tailscale 把所有机器串成一个私有网络。Tailscale 是一个组网工具，在每台设备上装好并登录同一个账号，这些设备就自动组成一个互通的虚拟内网，每台拿到一个固定的 100.x 开头的内网 IP。手机、笔记本、云服务器、家里的机器，互相都能直达，不用公网 IP，不用端口转发，也不用暴露到公网。

Tailscale 管理的是网络，不是 Hermes 本身。Hermes 该配的认证、白名单、密钥这些还是都需要配置，组网只是让你不用把这些东西暴露到公网上。

## 怎么选

在不同的场景可以用不同的方式。个人电脑上，日常对话和写东西用桌面应用或者 TUI，图形界面的用桌面，远程 SSH 就用 TUI。

但是对于最合适的方式，还是需要打开网关，然后通过聊天工具（比如 tg）+ Hemrs 的方式来使用。这种方式也是最符合未来 Agent 的形式的，Agent 需要随时响应，不能每次使用的时候，都打开电脑。

目前基本上每个人都离不开手机，所以通过手机来触发也是最合理的方式，我目前也在做一个移动端，希望能解决在移动端上的使用。

# 2026-08-28

# Hermes 残酷共学｜日常配置和常用技巧，让 Hermes 自己做更多的事情

在安装完 Hermes 之后，就可以用起来了，虽然在大多数时候，直接把自己的需求整理成文字然后发给 Hermes 就可以，然后让 Hermes 来完成剩下的工作。

但是这样用起来 Hermes 几乎就是一个黑盒，你不知道它内部到底是怎么执行的，所以需要掌握一些基础的命令和配置，让 Hermes 在运行的过程，能够暴露出一些信息，让我们更容易观察到 Hermes 的状态，以及控制它的执行行为。

## Hermes 常用命令

Hermes 内置了很多的命令，这些命令可以用来执行对 Hermes 的行为进行控制，或者更改 Hermes 的配置。

无论是使用 tui、桌面端或者 tg 使用 Hermes，所有触发的方式都是一样的，使用斜杠触发。

tui 中触发。

![Pasted image 20260828080746.png](https://raw.githubusercontent.com/rayjun/hermescn-assets/main/Pasted%20image%2020260828080746.png)

tg 中触发。

![Pasted image 20260828080821.png](https://raw.githubusercontent.com/rayjun/hermescn-assets/main/Pasted%20image%2020260828080821.png)

Hermes 桌面端中触发。

![Pasted image 20260828080839.png](https://raw.githubusercontent.com/rayjun/hermescn-assets/main/Pasted%20image%2020260828080839.png)


Hermes 中内置的这些命令是一段内置程序，不是 skills。每条命令在 Hermes 的命令注册表里都有定义，包含命令名、说明、参数格式和所属分类，背后是写好的处理逻辑。比如 `/new`，执行的是开新会话那段程序，`/model` 用来更换大模型。这些命令的行为和入口无关，TUI、桌面端、Telegram 里表现一致。

skills 存在 `~/.hermes/skills/` 目录里，内容是完成某类任务的步骤、命令和注意事项，agent 干活前先读它照着做。技能安装之后也会生成斜杠命令入口，比如用 `/learn` 学会的技能，之后发 `/技能名` 就能直接触发。从本质讲，命令是程序，技能是说明书。命令表之外，config.yaml 里还能自定义 `quick_commands` 快捷命令，把常用话术绑到斜杠上。

Hermes 内置的命令很多，还可以安装更多的 skills，但是对于大多数命令，都不需要死记硬背，因为几乎所有的这些命令和 skills，我们都可以使用自然语言来触发。

在日常使用中，更合适的习惯是使用自然语言来触发，这个更适合未来 Agent 的打开方式。所以对这些命令有一个

### 常用命令

`/new` 开新会话 session。

`/title 名字` 给当前 session起标题，方便以后找回。

`/compress` 手动压缩上下文，长对话越聊越慢的时候用它，把前面压缩成摘要，腾出空间继续聊。

模型相关的还有 `/model` 切换模型、`/reasoning` 调整思考强度。写复杂代码把思考强度调高一档，简单问答调低，思考的复杂度越高，那么响应的速度就会越慢。

单轮问答之外，Hermes 还有一套目标机制，适合跨多轮才能完成的事。发一条

```bash
/goal 把仓库里 review 标注的问题全部修完，每个问题都要有验证
```

想中途加条件，就是用 `/subgoal`。当前任务跑了一半，你想补一条条件，直接

```bash
/subgoal 顺带把 README 也更新了
```

在当前 session 中，可以让 Hermes 派出独立子代理。子代理有自己独立的上下文，跟当前这个互不干扰，可以并行干活和独立检查。

让另一个它来审查刚做完的工作，用 `/review`。

```bash
/review 检查这个 PR 的改动有没有安全问题，逻辑漏洞，以及测试覆盖
```

想看看现在有几个子代理在跑、后台任务进展如何，用 `/agents`（别名 `/tasks`）。派出去的审查子代理、正在跑的后台任务，都能从这里看到状态。

没有单独的 `/subagent` 命令。日常用法就两种，审查工作用 `/review`，看子代理和后台任务的状态用 `/agents`。想并行处理多个独立任务，直接跟它说"派个子代理去查这个、再派一个去查那个"，它自己会用工具调度。

另外 Hermes 中有一个越用越好用的机制。Hermes 会把重复要做的事保存成 skills，后续使用一句话就能触发。

比如一个写作流程，可以用 skills 检查文本有没有违规词、调整文章风格、检测专属的写作禁忌，每一条都是一个 skills。可以将多个 skills 组合成自己的工作流。

在 Hermes 把工作经验变成技能有三种方式，分别是 `/learn`、`/refine` 和直接在对话里让 agent 用 `skill_manage`。

`/learn` 是显式的技能学习命令。后面可以加上具体的信息来源，比如书籍、网址、还可以是"刚才这段对话"都可以，它会把这些材料整理成一份符合规范的 skills 并存进目录，之后用 `/skills 麦城` 触发。

`/refine` 是隐式的经验整理。它把当前整段对话过一遍，值得记住的判断和偏好写进记忆，能复用的流程存成技能。

还有一种就是直接在对话里说"把上面的流程流程存成技能"，agent 调 `skill_manage` 完成。

所有 Hermes 有一种活人感，很多时候，教过一次的事，不用第二次教，这是 Hermes 和普通聊天工具差别最大的地方，自己很多做事的方式和经验都会在 Hermes 沉淀，而且所有的这些数据都还是由自己控制的。

## 元 skills hermes-agent

Hermes 自带一个特殊技能，叫 hermes-agent，一般来说会隐式触发，也可以使用斜杠来触发。这个技能的内容是 Hermes 自己的说明书，命令行参考、全部斜杠命令、配置文件路径、常见故障排查、开发贡献规则都在里面。

![Pasted image 20260828145042.png](https://raw.githubusercontent.com/rayjun/hermescn-assets/main/Pasted%20image%2020260828145042.png)

它的用途是让 agent 在配置、扩展或调试 Hermes 自身时有明确的规则。我让它改配置、查命令、排查网关问题的时候，它会先加载这个元技能，按里面的官方命令清单和排障步骤干活，而不是凭训练记忆瞎试。想改哪项配置、有哪些斜杠命令、日志在哪里，这个技能里都有答案。

在对话里临时加载用 `/skill hermes-agent`，装好之后它会在 agent 准备处理 Hermes 相关任务时自动出现。这算元技能的典型用法，用一套关于工具自己的知识，让工具正确地操作自己。

这个 skills 可以说是 Hermes 中最要的一个 skills，可以认为是所有 skills 的元 skills。

## md 文件的配置

在 Hermes 中，需要自己配置一些关键的 md 文件，Hermes 可能会根据这些不同的 md 文件做出不同的气质的行为。

在配置的时候需要重点关注：

- SOUL.md：这个文件直接决定了你的 Hermes 的人格、语气、风格，会对你的产出产生很大的影响。在安装完 Hermes 之后有一个默认的文件，如果自己没有特别的需求可以不改动。每个 Hermes 的 Profile 有一个这个文件。
- AGENTS.md、hermes.md、CLAUDE.md：这些都是具体的项目规则，可以根据不同的项目进行编写，Hermes 在执行任务的时候会重点参考这些 md 文件中的规则。

另外 MEMORY.md、USER.md 都会由 Hermes 在运行的过程中自动更新，会记录工作过程中产生的偏好、约定和经验。

## 定时任务

Hermes 的定时任务是另外一个很重要的功能，可以用来完成一些周期性的任务，而且在定时任务中，可以直接调用 skill 来完成一些特定的工作和任务。而且可以单独为定时任务设置大模型，比如一些简单的定时任务就可以使用便宜的 LLM，这样更省 token。

我现在机器上挂了十几个定时任务，都是这么来的。DeFi 晨报周四周五早上九点推送，地址监控每十二小时查一次链上资产变动，AI 新闻素材每天早上八点整理好素材发到 Telegram。醒来直接过一遍就可以了，不用花很多时间去浏览信息。

## 为不同的场景设置不同的 LLM

除了可以在定时任务中设置不同的 LLM 之外，还可以为更多的场景来设置不同的 LLM，比如在视觉、上下文压缩、MCP 等场景，都可以设置不同的 LLM。

这个功能叫 Auxiliary Model，这个同样不用担心配置，可以直接交给 Hermes 自己来配置。

![Pasted image 20260828151738.png](https://raw.githubusercontent.com/rayjun/hermescn-assets/main/Pasted%20image%2020260828151738.png)


## 让 Hermes 自己做更多

在大多数情况，这些配置和命令其实都可以忘记，在使用 Hermes 的时候，要邀请更多使用自然语言来触发。尽早把 Hermes 培养成一个真正的 Agent 助手，而不仅仅是一个工具。这种真正的 Agent 助手，才是未来 Agent 能大规模使用的形态。

因为我认为在 AI 越来越普及的时候，我们更需要让自己使用的 AI 更加可控，而不是直接使用别人提供的黑盒，比如 Grok Bot，虽然在体验上确实不错，但是自己完全失去了对 Agent 的控制，自己用的越多，那么自己交出去的数据就越多。而且在长期使用 Agent 的过程中，我们还会通过 Agent 把自己的经验和性格都蒸馏出来，这些数据最好还是能被自己掌握。

基于这个原因，也是我认为最好使用开源可控的 Agent 的原因，目前来看，Hermes 可能是最适合的那个。

# 2026-08-29

# Hermes 残酷共学｜Hermes 不是许愿池，把模糊需求变清晰

很多人还在把 Hermes 当作许愿池来使用，其实不止是 Hermes，还有其他类型的 Agent，在能力上已经很强了。

现在的瓶颈已经是怎么人，很多时候，如果 Agent 没有产出让我们满意的结果，那么问题可能不是出在 Agent 上，而是我们自己在表达上没有让 Agent 理解，没有给到足够多的信息。或者是一次性给的信息太多了，Agent 单个上下文无法一次性理解这些信息。

解决的办法，不是把每句话说得更细。一句话写得再长，也装不下你脑子里的全部背景。要把任务放进结构化的框架里，让语义由固定的上下文来定住。我把这些问题总结出四个层面，从大到小，不仅仅是在 Hermes 中适用，也可以扩展到其他的 Agent。

## 第一层，定制 SOUL.md 的风格

Hermes 每次开新对话，系统提示词的第一位就是 `SOUL.md` 的内容。这份文件定义它是谁、用什么语气、遵守什么原则，相当于它的性格说明书，完整替换掉内置的默认身份。

它对你的产出影响比大多数人想象的大。同样是一句**写个总结**，SOUL 里写**直接、克制、每个判断要有依据**，它写出来是干净的文字。SOUL 里写**热情、全面、多鼓励**，它写出来能凑满两页。同样的模型，同样的命令，产出的风格也会完全不同。

安装完 Hermes 会有一份默认的 SOUL.md，但是这个默认的不一定适合你，可以根据自己的工作内容改一版，那么后续所有任务都会收到 SOUL.md 文件的影响。

它不用每次设置，这个配置长期生效。这一层解决的是风格和个人的特质问题，你不用每次都说”写清楚一点“，”别啰嗦“，“用中文回答”，SOUL 已经把这些信息都直接传递给 LLM 了。

**延伸阅读**
- Hermes 官方 SOUL 指南 [Use SOUL with Hermes](https://hermes-agent.nousresearch.com/docs/guides/use-soul-with-hermes)
- Hermes 系统提示词组装原理 [Prompt Assembly](https://hermes-agent.nousresearch.com/docs/developer-guide/prompt-assembly)

## 第二层，积累自己的 prompt 库

有人觉得 Agent 出现之后，prompt 就不重要了，其实不是的，反而 Prompt 更加重要了。

Agent 改变的只是 prompt 的用法。以前是每次手写一段话，现在可以把它变成资产，一次写好，反复调用。我用的写作流程就是例子。检查文本有没有违规词、调整文章风格、检测我专属的写作禁忌，每一条都是一段写好的 prompt，然后让 Hermes 整理为 SKills，每次写完文章都会跑一遍。第一次写它们花了些时间，之后每篇文章都是同一套流程。

平时把好用的 Prompt 告诉 Hermes，然后 Hermes 就会自动把这些 Prompt 转换为 SKills，不用每次从头组织语言。

积累 prompt 库没有门槛，可以从日常的工作开始。存得多了，你在某个领域里让 Agent 干活的质量会明显稳定。

**延伸阅读**
- OpenAI 官方 [Prompt Engineering Guide](https://platform.openai.com/docs/guides/prompt-engineering)，六条策略，写 prompt 的入门标准
- Anthropic 官方 [Prompt Engineering Overview](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview)，偏长对话和工具调用场景
- Hermes 技能体系 [Skills](https://hermes-agent.nousresearch.com/docs/user-guide/features/skills)，prompt 库在 Hermes 里的落地方案
- [superpowers](https://github.com/obra/superpowers)，社区里最完整的可复用技能集合，虽然这套东西在使用 Hermes 之后我已经不用了，但整体设计还是很值得思考

## 第三层，项目模板和 AGENTS.md

光有风格和通用 prompt 还不够。不同任务的区别很大，写代码和写教程是两个完全不同的任务，做研究和做运维也不是一回事。每个领域应该有自己的项目模板。

Hermes 的项目规则就是这个用法的载体。每个项目目录里可以放一份 AGENTS.md，写清楚这个项目是干什么的、有什么约定、代码怎么组织、测试怎么跑。Hermes 进到那个目录会自动读它，开工前先知道规矩。我所有的项目里都有这个文件，比如在以太坊客户端代码里写共识路径优先、测试要可复现，写文章的目录里写文件名规范、提交信息格式，每个项目的规矩都固化成文件，不用每次重讲。

同样的需求，在不同项目里执行，它的行为就不一样，因为每个项目的 AGENTS.md 给的上下文不同。各项目把一类任务的固定背景留下来，后续可以在不同的项目中直接复用。

一个类型的项目如果执行的频率很高，花十分钟写一份 AGENTS.md，长期是划算的。写的时候不用追求全，把最容易跑偏的地方写清楚就够了，后面用着不顺的时候可以随时调整。

**延伸阅读**
- [agents.md](https://agents.md/)，AGENTS.md 开放格式规范站，可以用于日常项目的参考

## 第四层，用 Hermes 自己的能力兜底

前三层解决的是任务开始之前，把背景和风格定下来。任务开始之后，还会遇到新情况，这时候靠 Hermes 的机制来保证执行质量。

`/goal` 能把目标变成一份带验收标准的契约。如果直接跟它说"把网站改好"，它不知道怎样算完成，可以换成用 `/goal draft 页面打开速度变快，用 Lighthouse 测，性能分不低于 90`，它整理出包含检查步骤的完成规则，每一轮都按这个标准验收。

`/review` 能派一个独立的子代理来审查刚做完的工作。它没有前文的上下文，从不知道你怎么想的视角重新看一遍，能查出顺着思路走漏掉的问题。写完代码让子代理查逻辑漏洞和测试覆盖，比自查可靠。

`/subgoal` 在任务进行中补条件，在不用中断任务的前提下补充新的条件。E2E 测试则让它在真实流程里自己验证，我在 Mac 上做移动端开发，用 `/goal` 触发它跑完整的端到端测试，所有功能调试完成，期间不需要人为干预。

前三层保证它听懂任务，这一层保证它做对事情。任务描述得再清楚，执行中也会有意外，这些机制就是处理意外的。

**延伸阅读**
- Hermes 官方 [/goal 机制](https://hermes-agent.nousresearch.com/docs/user-guide/features/goals)，目标契约的完整说明
- Hermes 官方 [Delegation 子代理](https://hermes-agent.nousresearch.com/docs/user-guide/features/delegation)，/review 和 /agents 背后的机制
- [12 Factor Agents](https://github.com/humanlayer/12-factor-agents)，把 Agent 当服务设计的十二条原则，harness 层面的设计参考


## 单次会话也要有结构

除了上面四个层面之外，我还有一个习惯，作用在每一次单条指令上。我交代任务习惯说三件事，做什么、交付什么、怎么算完成。

"把这个项目的几个问题修一下"这种表达很难让 Agent 理解你的目标是什么。可以换一种说法，"看下 XX 项目中标注待修的那几个问题，按照批注的任务修复，改完发我一份清单，每项写清楚改了什么、怎么验证的"。

这样一来，在一句话中把做什么、交付什么、怎么算完成都说清楚了，那么它交回来的东西质量就会有很大的提升。

这个习惯和前面四层不冲突。长期上下文负责风格和约定，单条指令负责这一次的具体目标和验收。

## 最后

把模糊需求变清晰，不是要求你学会写完美的 prompt，而且 prompt 可以长期慢慢优化。

上面所说的四个层面都是从固定的地方组织上下文，SOUL 定风格，prompt 转化为固定的 SKills，AGENTS.md 定项目规矩，Hermes 做最后的执行。

多数人头疼的产出不符合预期，可能问题不是出在模型不够聪明，如果养成了好的习惯，那么与 AI 的交互就会轻松很多，也不用把 Hermes 或者其他 Agent 当作许愿池。

# 2026-08-30

# Hermes 残酷共学 ｜Seesion 是临时状态，Agent 需要一个稳定的身份

当前大多数 Agent 都是 session 模式。如果你当前在 Hermes 也还是使用 Session 模式，那么你应该试试 Hermes 的 Bot mode。

无论是 Codex 还是 CC 这类已经被验证过的 Agent，都还是以 session 的模式在使用。但 session 的模式本质上还是把 Agent 当工具在用，每次有需求就告诉它，它获取当前的上下文信息或者项目信息，然后调用 LLM 来做后续的事情。

但是 Agent 其实可以做更多，比如可以为 Agent 安排特定的身份，在软件开发过程中，通常会涉及到开发、code review、测试等等。

如果直接把所有的这些功能和角色放在一个上下文中，那么上下文很快就会被填充满，然后就会导致出现很多预期之外的行为，导致执行的效率下降。

那么在 Hermes 中，通过 bot mode 可以来解决这个问题。另外最近很火的 grok bot 也是同样的思路，把 Agent 从 Session mode 中解放出来，为 Agent 安排长期的身份和角色。

## Hermes 中的 Session 和 Bot

当前无论是通过哪种方式访问 Hermes，模式都是 session 模式，包括通过 tg 连接，同样是基于 session。在 session 模式下，每次都是共用一个 profile，包括 SOUL.md、记忆、skills。这样时间长了之后，一个 profile 通常都会膨胀，导致后来效率越来越低。

![Pasted image 20260830151755.png](https://raw.githubusercontent.com/rayjun/hermescn-assets/main/Pasted%20image%2020260830151755.png)



你的配置、密钥、技能、定时任务，全绑在同一个 Hermes profile上。

但好在 Hermes 在设计之初就支持多 profile，一个 profile 就是完整独立的一套 Hermes，有自己的配置文件和密钥文件，自己的人格文件，自己的记忆、会话、技能、定时任务和状态数据库。

Profile 的好处，最容易在 bot mode 中看到。你能同时跑几个 Hermes bot，各用各的记忆、各用各的人格。官方文档给 Profile 举的例子就是这样，编码助手、个人 bot、研究 agent，各一套。一个群里，写文章的 bot 和监控数据的 bot 可以同时工作。

而且最终要的是，可以把多个 bot 拉到一共群聊中，然后围绕同一个项目进行协作。这种才是 Agent 的正确打开方式。

这样每个 bot 的身份、skills、记忆完全隔离，在对同一个项目工作时，也不容易在同一个错误的方向上越做越错。如果做开发的 bot 方向错了，那么 review 的 bot 就能把及时发现。

![Clipboard_Screenshot_1788074726.png](https://raw.githubusercontent.com/rayjun/hermescn-assets/main/Clipboard_Screenshot_1788074726.png)

但是目前也还是有一些小的缺点，Hermes 中 bot mode 暂时只能通过插件的形式安装，只能在桌面端使用。

在 tg 中，可以通过创建多个 profile 来自动配置这种多 profile 模式，让多个 profile 之间可以相互协作。


## bot 的扩展性

为什么 bot mode 比 session 模式更好呢？这其实和管理的成本有关，当前很多 Agent 其实已经支持了 subagent 模式，在执行任务的过程中，可以把任务拆分，然后交给一个上下文很干净的 Agent 去做。

但是这种模式下，agent 都还是一次性的，做完事情之后，Agent 就消失了。下次需要的时候还需要重新启动。

但是如果是要建立一个稳定的工作模式或者做事流程，很多 Agent 需要固定下来，而不是每次都创建新的。

这种情况下，bot 的扩展性就很好，可以根据需要创建任意新的 bot，但是 bot 不是一次性的，而是可以直接融入到当前的工作流程中。

每个 bot 在工作的过程中可能也会启动新的 subagent 来做具体的执行，执行完成之后 subagent 就不存在，而 bot 本身则能稳定存在。 


## Hermes 的未来模式

当前 Hermes 的 bot mode 当前还是以插件的形式在提供，但是我觉得以后 bot 模式肯定会成为多 Agent 协作的主流。

对于普通用户来说，可以直接启动多个 Agent bot，并分配不同的工作内容，底层的 Agent 和 profile 的配置对于用户来说其实都是可以屏蔽的。

# 2026-08-31

# Hermes 残酷共学 ｜授权和审核，让 Hermes 的权力有边界

其实这一部分的内容是最无聊的，而且平时在使用的过程中还会觉得一直点审批很无聊。事实上也是这样的，而且很多时候，审批的内容根本就不会看，直接点击通过。

如果是使用 Codex，CC 这些，直接开启 yolo 模式，然后把一切都交给 Agent，甚至有些 Agent，比如 Pi，直接就是 yoloy 模式，如果你想开启审批模式，还需要额外安装扩展。

如果一个 Agent 让你感觉越智能，越好用，那么就说明你给它的权限就越大。

Hermes 在授权这块的设计做了灵活的空间，可以根据自己的需求灵活进行调整。

但是 Hermes 最好还是在一个相对独立的环境中使用，因为它手里握着执行命令、读写文件、联网发消息的完整权限，一个错误的指令就可能把机器上的数据删掉。

权限不能不给，要不然用起来就像是智障，给了又不能没有约束，于是 Hermes 在中间加了一道闸，这道闸内置一份危险命令清单，命中清单的命令不直接执行，先停下来等人确认。

## 常规权限审批

这份危险清单维护在源码里，叫 DANGEROUS_PATTERNS。常见的几条是递归删除（rm -rf 一类）、chmod 777 放开文件权限、pkill -9 强杀进程、dd 直接写磁盘、SQL 里 DELETE 不带 WHERE、格式化磁盘、停系统服务。

命中这些模式，命令进入审批，不命中就正常运行。比如 rm 的参数换个顺序也会命中，Windows 下的 del、Remove-Item 同样有对应的规则。

审批有几种模式。我机器上 config.yaml 里 approvals.mode 是 manual，碰到危险命令就停下等人确认，timeout 是 60 秒，超时没有回应，命令直接拦下来。

另外两种模式，smart 会让一个辅助模型先判断，低风险自动放行，高风险再问人，觉得 manual 太啰嗦就可以换成这种模式。off 等于全部跳过，一般不推荐。

在 Telegram 里用 Hermes，审批命令会以 pending 状态挂起，回复 /approve 就是同意，/deny 就是拒绝。超时被拦之后，让 Hermes 重试一次，提示会重新出现，再点确认就行。

想临时跳过审批，有 --yolo、会话里发 /yolo、设环境变量 HERMES_YOLO_MODE=1 三种方式。yolo 只跳过命令审批这一层，密钥脱敏是另一套机制，不受影响，别指望开了 yolo 就能看到明文密钥。

但即使是在 yolo 模式，像 rm 这类的高危命令依然需要审核，不能默认通过。

## 其他的安全规则

命令审批之外，Hermes 的权限还分成好几层。

密钥脱敏默认开启。工具输出、日志里出现的 API key 和 token，在进入上下文之前会被自动打码，避免密钥泄露到对话和日志文件里。

密钥本体放在 ~/.hermes/.env，OAuth 凭据存在 auth.json，添加凭据用 hermes auth add，查看用 auth list，可以配多个 key 自动轮换。

工具集可以按平台单独开关。不需要的能力直接关掉，比如不让 Agent 生成图片，就把 image_gen 这个工具禁用，它在对话里就调不到这个能力。

上一篇文章讲过的 profile 隔离也是授权的一部分，每个 profile 的配置、密钥、技能完全独立，一个 profile 默认动不了另一个 profile 的东西。

## 日常使用技巧

下面是我在使用 Hermes 中的一些使用技巧，尽可能在保证 Hermes 自由度的前提下，保证安全。

- 定时任务要配 cron_mode approve。无人值守的定时任务如果每次都等人批命令，那就没办法执行了。我机器上的 cron 配置就是 approve，定时任务自动放行，手动会话保持 manual，危险操作仍然有人把关。
- 密钥只放 .env，不写进代码和文章，密钥脱敏保持开启。
- curl 管道接 python 这类写法会被拦，先 -o 落盘，再单独解析，既绕开审批又留了中间文件。
- 敏感项目用独立 profile 跑，配置、密钥、技能天然隔开，其他的 profile 无法访问，项目做完之后可以直接把 profile 删除


## 还有哪些问题

当前 Hermes 还有其他 Agent 的审批模式做的其实都不好，每次需要审批的时候，待审批的命令的可读性太差了。

最后就是直接不看，然后点同意，这样一来，审批就没有意义了。

要改善这个问题，首先需要改变审批的呈现形式，提高审批命令的可读性以及可能会造成的后果，然后再让用户审批。

另外，对于大多数的命令其实每必要审批，直接放行就可以了，当前 Hermes 的 smart 模式尝试在解决这个问题，但是还不够好，这里可能需要引入 LLM 的能力来判断一个操作可能会造成的后果。
